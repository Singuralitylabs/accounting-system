# 機能設計書

## 1. システム概要

### 1.1 システム名

経理システム

### 1.2 目的

未来技術推進協会のための案件処理、経理処理、取引先管理を効率化するウェブアプリケーション。

### 1.3 対象ユーザー

- 一般ユーザー: 案件作成・管理を行うメンバー
- チームリーダー: 自分のチームの案件を管理するメンバー
- 経理担当者: 案件の確認・承認を行うユーザー
- 管理者: システム全体の管理を行うユーザー

## 2. システムアーキテクチャ

### 2.1 開発環境

- フレームワーク: Next.js (App Router)
- 言語: TypeScript
- UI: Tailwind CSS, Mantine UI
- データベース: PostgreSQL (Supabase)
- 認証: Supabase Auth (Google OAuth)
- ホスティング: Vercel

### 2.2 システム構成

```
Frontend (Next.js) <--> Server (Next.js API Routes) <--> Database (Supabase)
```

### 4.1 ユーザー認証 (F001)

#### 4.1.1 概要

- Google アカウントを使用した OAuth 認証
- 未来技術推進協会のドメイン(`future-tech-association.org`)のみログイン可能

#### 4.1.2 フロー

1. ログイン画面で Google ログインボタンをクリック

### 4.16 月次損益計算書表示 (F017)

#### 4.16.1 概要

- 月を選択すると、その月の損益計算書を表示する
- 月次損益はスプレッドシート運用と同じ「粗利 → 管理費 → 経常利益」の構造で表示する
- 計算式:
  - **売上総利益（粗利） = 売上合計 − 案件費用合計**
  - **経常利益 = 粗利合計 − 管理費合計**（＝ 売上合計 − 案件費用合計 − 管理費合計）

#### 4.16.2 計上ルール

| 区分         | 計上月の判定                                                     | 金額                                                                                                   |
| ------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 売上         | 所属案件の matters.start_date（案件開始日）の属する月            | business.amount                                                                                        |
| 案件費用     | 所属案件の matters.start_date（案件開始日）の属する月            | costs.price                                                                                            |
| 管理費       | 定期費用マスタの支払月（適用期間内かつ支払サイクルに一致する月） | recurring_costs.price（支払月に全額計上）                                                              |
| 経理追加収支 | extra_entries.entry_date（日付）の属する月                       | 収入の請求額（billing_amount）は売上合計へ、経費（expense_amount。収入・支出共通）は案件費用合計へ算入 |

- 案件の売上・案件費用は、請求日（invoice_date）・支払い期限（period）に関わらず、所属案件の案件開始日の月に全額計上する（Issue #146。1 案件の収支が必ず同じ月に載り、月次で案件単位の損益を読めるようにするため）。数ヶ月にまたがる案件も開始月に全額計上する。invoice_date / period は損益計算書の計上判定には使わない（案件管理・経理処理上の請求日・支払期限としては従来どおり使う）
- この基準は過去の月にも遡って適用する（月ごとに基準を切り替えない）。旧基準（請求日・支払い期限の月）の月に付いていた損益調整は、マイグレーション 25 で案件開始日の月へ付け替えた（[docs/database.md 3.13](database.md#313-profit_loss_adjustments-テーブル)）
- **下書きの案件は損益計算書に計上しない**（`is_fixed = false` かつ `is_completed = false`。NULL は false 扱い）。月次・年間推移・月未確定の注記・チーム別内訳のいずれにも含めない。経理申請した時点で計上され、経理が「下書きに戻す」と計上から外れる。判定は `isDraftMatter`（`app/utils/profitLossLogic.ts`）と取得側の絞り込み（`matterPeriodFilter`）で同じ定義を使う
- 月の判定は日付文字列の先頭 7 文字（YYYY-MM）の比較で行う（タイムゾーン変換による月ズレを避けるため Date オブジェクトは使わない）
- 案件開始日が NULL の案件（下書きを除く）の売上・費用と、entry_date が NULL の経理追加収支は「月未確定」として売上・費用の合計を別枠表示する（新規作成時は開始日が必須だが、既存案件には NULL があり得る）
- business.amount は NULL 許容のため、集計時は NULL を 0 として扱う
- 定期費用の計上判定: 適用期間内（`start_month <= 選択月の月初日 AND (end_month IS NULL OR 選択月の月初日 <= end_month)`。end_month の月**を含む**）かつ支払月に一致する月
- 支払月は適用開始月を起点に支払サイクル間隔ごとに自動計算する（月払い=毎月、四半期払い=3ヶ月ごと、年払い=12ヶ月ごと）。月割り按分は行わず、支払月に全額計上する
- 経理追加収支はマイナス金額を許容する（案件側のデータを直さずに損益計算書上で減額調整するため）。収入の請求額は売上へ、経費は案件費用へ算入し、案件別収支ではエントリのチームの「経理追加収支（案件外）」行、分類別収支ではエントリの分類へそれぞれ振り分ける
- 損益調整（実績額修正）がある明細行は、集計・表示のすべてで実績額（= 元データ + 調整）を用いる（[4.16.5](#4165-損益調整実績額修正)）

##### 案件別収支の集計ルール（Issue #147）

案件の収支は「案件別収支」として チーム → 案件 → 案件内訳 の階層で集計する。売上・案件費用の明細はいずれもちょうど1つのチーム・1つの案件（経理追加収支は案件外）に属するため、チーム小計の合計は売上合計・案件費用合計と必ず一致する。

| 対象                       | 集計するチーム / 行                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------- |
| 売上（business）           | 案件のチーム（matters.team）→ 案件行                                                                    |
| 案件費用（costs）          | 案件のチーム（matters.team）→ 案件行                                                                    |
| 経理追加収支の請求額・経費 | エントリのチーム（extra_entries.team）→「経理追加収支（案件外）」行。チーム未指定は「全体共通」グループ |

- 並び順: チームは管理画面の項目管理（select_options のチーム）の並び順（display_order）。マスタに無いチーム（無効化・削除済み）はその後ろに名称順、「全体共通」は最後。案件は案件 ID の昇順。案件内訳は売上明細 → 費用明細の順で、それぞれ ID の昇順。「経理追加収支（案件外）」行は各チームの案件行の後ろ
- 案件の粗利 = 案件の売上（売上明細の実績額合計）− 案件費用（費用明細の実績額合計）。売上のみ・費用のみの案件も片方を 0 として表示する
- 不変条件: チーム小計の合計 = 案件別収支の合計 = 分類別収支の合計 = サマリーカード（売上 / 案件費用 / 粗利）

##### 分類別収支の振り分けルール

分類別収支は売上分類（大分類）別に 売上 − 案件費用 を集計する。売上・案件費用はいずれもちょうど1つの分類に属するため、分類別収支の合計は「売上合計 − 案件費用合計」（= 案件別収支の合計）と必ず一致する。

| 対象                       | 集計する分類                             |
| -------------------------- | ---------------------------------------- |
| 売上（business）           | 案件の分類（matters.category）           |
| 案件費用（costs）          | 案件の分類（matters.category）           |
| 経理追加収支の請求額・経費 | エントリの分類（extra_entries.category） |

- 売上のない分類に費用のみが計上された場合（支出エントリなど）は、粗利がマイナスの行として表示する
- 分類の値はマスタ（select_options）に追従し、特定の分類項目には依存しない。小分類別の集計は行わない（大分類まで）
- 並び順は粗利の降順
- 案件費用の品目別集計は行わない（品目は案件内訳の費用明細行に表示するのみ。Issue #147）
- 管理費は費目（recurring_costs.item。select_options の item と同じ値域）別に集計する

#### 4.16.5 損益調整（実績額修正）

- 案件の売上・案件費用・管理費が実際の入金・支払額と一致しない場合（請求額の変更、値引き、ある月だけ金額が異なる定期費用など）に、経理担当者・管理者が損益計算書の月次タブ上で、対象月の実績額へ修正できる
- 元データ（business.amount / costs.price / recurring_costs.price）は一切書き換えず、対象行×対象月ごとの調整（差分）を別テーブル（profit_loss_adjustments）に保持する。損益計算書は「元データ + 調整 = 実績」として表示・集計する
  - 案件の売上・費用はチームリーダーの入力であり経理申請後の編集が差し戻し検知の対象になるため、経理が直接書き換えると担当者の見ている案件が変わり差し戻し検知も誤発火する
  - 定期費用マスタは適用期間で全月に反映されるため、金額欄を直すとある月だけでなく全月が変わってしまう。恒久的な改定は従来どおり「打ち切り＋新行」運用（[4.18.4](#4184-金額改定の運用)）とし、単月の差異のみ本機能で扱う
- 入力は実績額のみ。保存時にシステムが調整額（= 実績額 − 保存直前の元データ金額）を計算し、その時点の元データ金額（スナップショット）と調整理由（必須）とともに保存する。実績額を元データと同額に戻すと調整レコード自体が削除される
- 調整の追加・更新・削除は明細行単位で即時保存する（マスタデータ管理のようなステージング方式にはしない。行単位の操作の方が誤りが起きにくいため）
- 元データ変更の検知: 調整の保存後に元データの金額が変更された場合、対象の明細行に「元データが変更されています」の警告を表示する。調整額は自動では追従しない（経理が再確認して実績額を更新するか、調整を削除する）
- 対象行が別の月に移動した場合（案件開始日の変更等）・対象行の案件が下書きに戻された場合: 調整は対象月に留まるため、その月の集計対象に対象行が無ければ損益には反映せず、「対象行が当月に存在しません」として削除を促す警告を表示する
- 対象行（business / costs / recurring_costs）そのものが削除された場合は、調整も自動的に削除される
- 確定済みの月（[4.16.7](#4167-月次収支確定issue-148)）の調整は追加・更新・削除できない（「確定済み」をオフにしてから編集する。DB の Row Level Security と保存関数でも拒否する）
- 経理追加収支のマイナス金額による減額調整（[4.19.1](#4191-概要)）とは役割を分ける。案件・定期費用マスタに紐づく差異は本機能（損益調整）で、それらに紐づかない収入・支出は経理追加収支で扱う
- 権限: 編集は経理担当者・管理者のみ（DB の Row Level Security でも担保）。チームリーダーは実績額・調整ありの表示・調整理由を閲覧できるが、編集操作は表示されない。他チームの調整は閲覧できない（ただし自分が作成した他チームの案件の売上・費用の調整は、その明細自体が見えるため閲覧できる。確定済みの月の確定明細と同じ範囲）

#### 4.16.6 表示タイトルの変更（Issue #150）

- 経理担当者・管理者は、損益計算書上の案件・明細の名称（タイトル）を、損益計算書上だけで有効な表示タイトルに変更できる（案件名はチームリーダーが案件管理用に付けた名前のため、経理が報告資料として読むには分かりにくい場合があるため）
- 対象: 案件別収支の案件行、案件内訳の売上明細（business 行）・費用明細（costs 行）、管理費の明細（recurring_costs 行）。**チーム・分類・品目・費目の見出しと経理追加収支（/extra-entries で内容を直接編集できる）は対象外**
- 適用範囲: 対象行単位で全月共通（月ごとに別のタイトルは持たない。定期費用も全月共通）
- 元データ（matters.title / business.name / costs.name / recurring_costs.name）は変更しない。上書きタイトルは損益計算書（月次・差分一覧・対象行が当月に存在しない調整の表示など、タイトルを表示する箇所すべて）でのみ使い、案件画面・経理用一覧には影響しない（差し戻し検知 has_updates も立たない）
- UI: 各行のタイトル横の編集アイコン → モーダルでタイトルを入力して保存（行単位で即時保存。損益調整と同じ）。空欄で保存すると上書きを削除し、元の名称に戻る。上書き中の行には「名称変更」バッジを付け、元の名称をツールチップで確認できる。前後の空白は除去し、200 文字以内
- チームリーダー: 上書き後のタイトルを表示する（編集操作は表示しない。DB の Row Level Security でも拒否される）
- 月次収支確定との関係: タイトルは金額・集計に影響しないため確定・変更検知・編集ロックの対象外とし、確定済みの月でも常に最新の上書きタイトルを表示する（確定明細に保存した名称は、元の行が削除された場合のフォールバックにのみ使う）
- 保存先: profit_loss_labels（[docs/database.md 3.14](database.md#314-profit_loss_labels-テーブル)）

#### 4.16.7 月次収支確定（Issue #148）

損益計算書は表示のたびに元データからライブ集計するため、締めた後の月でも案件の変更がそのまま過去の損益に反映され、経理が確認・報告した数字が後から黙って変わってしまう。月ごとに「確定」操作を設け、確定時点の収支を固定（スナップショット）して表示する。

##### 確定・確定解除（「確定済み」チェック）

- 月次タブに「確定済み」チェック（スイッチ）を置く（操作は経理担当者・管理者のみ）
  - **オン**（確認ダイアログあり）→ その時点の当月の損益計算書をスナップショットとして保存し、確定済みにする。明細はサーバ側で当月をライブ集計し直して保存する（クライアントから送られた金額は使わない）。保存後（編集ロックが掛かった後）にもう一度集計し、確定処理の最中に他の経理担当者が保存した変更があれば取り直す
  - 画面を開いた後に他の経理担当者が同じ月を確定していた場合（未確定の表示のまま残った古い画面からオンにした場合）は、既存の確定を上書きせず「既に確定されています。再読み込みしてください」と表示して最新の状態を読み直す（他の担当者の確定値・見送りを黙って置き換えないため）
  - **オフ**（確認ダイアログあり）→ 確定を解除する。スナップショットと変更の見送り記録（[4.16.7](#4167-月次収支確定issue-148) の変更検知）を削除し、ライブ集計の表示に戻る。損益調整・経理追加収支の編集ロックも解ける。既に解除されていた（別の画面・他の経理担当者が解除した）場合は、成功扱いにせず再読み込みを促す
  - オフにしてから再度オンにすると、その時点のライブ集計で新しくスナップショットを取り直す（確定者・確定日時は新しい確定のものになり、最終反映の記録・見送り記録は残らない）
- 確定の対象は **案件・定期費用・経理追加収支・損益調整のすべて**（月の損益を丸ごと固定する）。スナップショットに保存する明細:
  - 案件の売上明細（business）・案件費用明細（costs）: 元データ金額・調整額・実績額・調整理由、案件 ID・案件名・分類・チーム・取引先名 / コスト名・品目
  - 管理費（定期費用）: 名称・費目・チーム・支払サイクル・元データ金額・調整額・実績額・調整理由
  - 経理追加収支: 種別・分類・内容・チーム・日付・請求額・経費
  - 下書きの案件は含まない（[4.16.2](#4162-計上ルール)）。「月未確定」枠は確定の対象外（常にライブ表示）
- 確定月の順序制約は設けない（任意の月を確定できる。前月未確定でも当月を確定できる）
- 確定操作の履歴の全件保持はスコープ外。ヘッダに最新の確定者・確定日時（解除 → 再度確定で置き換わる）と最終反映者・反映日時のみ持つ

##### 確定後のデータ種別ごとの扱い

| 対象                   | 確定済みの月での編集                                                                    | 確定済みの月への反映                                                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 案件（担当者の編集）   | できる（ロックしない）                                                                  | すぐには反映しない。変更アラート → 経理が明細ごとに反映 / 見送り（下記「変更検知・反映・見送り」）                                |
| 定期費用マスタ         | できる（ロックしない。1 行が複数の月に効くため）                                        | **反映しない・アラートも出さない**。確定済みの月は確定時点の管理費のまま。反映したい場合は「確定済み」をオフ → 再度オンで取り直す |
| 損益調整（実績額修正） | **できない**（「確定済み」をオフにしてから編集する）                                    | -                                                                                                                                 |
| 経理追加収支           | **できない**（「確定済み」をオフにしてから編集する）                                    | -                                                                                                                                 |
| 表示タイトル           | できる（金額・集計に影響しないため対象外。[4.16.6](#4166-表示タイトルの変更issue-150)） | 常に最新のタイトルを表示する                                                                                                      |

##### 確定中の編集ロック（損益調整・経理追加収支）

| 対象                   | ロックする操作                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 損益調整（実績額修正） | `target_month` が確定済みの月の調整の追加・更新・削除（損益計算書の「実績額を修正」ボタン、対象行が当月に存在しない調整の削除ボタン）                                                |
| 経理追加収支           | `entry_date` が確定済みの月のエントリの追加・更新・削除、確定済みの月へ / からの日付の変更、確定済みの月への「前月の経理追加収支をコピー」（日付未入力＝月未確定のエントリは対象外） |

- UI: 該当する操作ボタンを無効化し、「確定済みの月です。編集するには損益計算書で『確定済み』をオフにしてください」とツールチップで表示する（損益計算書画面・経理追加収支画面の両方）。経理追加収支画面では確定済みの月のエントリの入力欄・削除ボタンを無効化し、日付の選択肢から確定済みの月の日付を除外する。保存時にもサーバ側で判定し、該当があれば何も書き込まずにエラーを返す
- DB でも担保する（Row Level Security。[docs/database.md 5.7 / 5.12 / 5.14](database.md#514-profit_loss_closings--profit_loss_closing_lines-テーブル)）。案件の明細・定期費用の削除に伴う損益調整の CASCADE 削除は妨げない（RLS は参照整合性の CASCADE には適用されない）

##### 確定後の表示

- 確定済みの月は、損益計算書（案件別収支・分類別収支・管理費）・サマリーカード・チーム別内訳・全体共通（参考）・年間推移のすべてを **スナップショットから** 表示する（未確定の月は従来どおりライブ集計）。確定明細はライブ集計と同じ集計処理（`aggregateMonthLines`）で集計するため、表の形はライブの月と同じ
- 名称（案件名・取引先名・コスト名・定期費用名）は金額・集計に影響しないため確定の対象外とし、元の行が存在する限り最新の名称（上書きタイトルがあればそれ）を表示する。元の行が削除された明細は確定時点の名称で表示する
- 月次タブに「確定済み（YYYY/MM/DD HH:mm 確定者: 氏名）」を表示する（反映の記録があれば「最終反映: 日時 氏名」も併記）。年間推移では確定済みの月の列見出しに鍵アイコンを付ける
- 定期費用マスタ画面（/recurring-costs）の各行に、適用期間に確定済みの月が含まれる場合は「確定済みの月（YYYY年M月〜）の損益計算書には反映されません」と注記する
- チームリーダーにも確定済みの表示と確定値を表示する（自チーム＋全体共通（参考）＋自分が作成した他チームの案件の範囲＝ライブ集計時と同じ範囲。確定明細の RLS で行単位に絞る。チェックの操作はできない）
- 確定済みの月でも「対象行が当月に存在しない損益調整」はライブの状態で判定して表示する。調整ごとに、対象行が確定明細に含まれていれば「確定値に算入済み」（確定後に外れた）、含まれていなければ「確定値にも含まれていません」（確定時点で既に外れていた）と表示し、削除は「確定済み」をオフにしてから行う
- 対象行が当月に存在しない損益調整の警告はライブの状態で判定して表示する（確定中は削除ボタンを無効化）

##### 変更検知・反映・見送り（Issue #149）

確定済みの月はスナップショットを表示するため、確定後に案件側で起きた変更はすぐには反映されない。確定後の変更を検知して経理に知らせ、経理が明細ごとに「反映」または「見送り」を選べるようにする。

- **検知の対象は案件（売上明細・案件費用明細）のみ**。定期費用マスタの変更は確定済みの月に反映せず、アラートも出さない（確定明細の管理費は常に確定時点のまま）。損益調整・経理追加収支は確定中はロックされ変更できない
- 確定済みの月について、当月のライブ集計の案件明細と確定明細（`source_type` が `business` / `cost` の行）を `(source_type, source_id)` で突き合わせて差分を算出する（純粋関数 `diffClosingLines`。`app/utils/profitLossDiff.ts`。DB トリガーや変更フラグは使わない。`matters.has_updates` の差し戻し検知とは目的が異なるためフラグも共有しない）
- 差分の種類:

| 種類     | 例                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| 追加     | 確定後に当月開始の案件が経理申請された / 明細が追加された / 案件開始日の変更で他月から移ってきた                   |
| 削除     | 案件・明細が削除された / 案件が下書きに戻された / 案件開始日の変更で他月へ移った / 案件開始日が未入力になった      |
| 金額変更 | 明細の金額の変更、明細削除に伴う損益調整の消滅で実績額が変わった                                                   |
| 区分変更 | 案件の分類・チームの変更（金額は同じでも案件別収支・分類別収支・チーム別の集計が変わる）。金額変更と同時もあり得る |

- 案件名・取引先名などの名称だけの変更は差分に含めない（金額・集計に影響しないため。表示名は上書きタイトルと同じく常に最新を表示する）
- 案件開始日の変更で案件が確定済みの月 A から確定済みの月 B に移った場合、A には「削除」、B には「追加」の差分が出る。差分一覧では相手側の月を併記し（「2026年9月へ移動」「2026年7月から移動」）、相手側の月も確定済みの場合は、片方だけ反映すると両月の合計がずれる旨を注意表示する。相手側の月の情報を取得できなかった場合は、この注意を出せないため差分一覧に再読み込みを促す注意を表示し、反映（選択した変更を反映・すべて反映）を無効にする（見送りは確定値を変えないため可能）。削除の差分には理由（他月へ移動 / 案件開始日が未入力 / 下書きに戻された / 削除された）を併記する

**変更があることを一目で分かるようにする（経理担当者・管理者）**

- 損益計算書画面を開いた時点で（どのタブ・どの月を表示していても）、ページ上部に警告バナー「確定後に未反映の変更がある月があります: 2026年8月（3件）/ 2026年9月（1件）」を表示する。月名をクリックすると月次タブのその月に切り替わる
- 月次タブ（確定済みで差分がある月）: 上部に「この月は確定後に N 件の変更があります」の警告と差分一覧。案件別収支の該当する案件行・明細行にも変更アイコンを付ける。差分一覧の選択は月を切り替えると解除する（他の月へ移動した明細は両月で同じ明細になるため、選択を持ち越すと選んでいない月で反映してしまう）
- 月ピッカー: 差分のある確定済みの月を強調表示する（確定済みの月は下線）。年間推移: 差分のある確定済みの月の列見出しにアラートアイコン
- 件数・アイコンは「未処理の差分」（反映も見送りもしていないもの）だけを数える。Slack 等への通知は行わない

**差分一覧と反映（明細単位）**

- 差分一覧の各行: 選択チェック・種類・区分（売上 / 案件費用）・チーム・案件名・明細名・変更前 → 変更後・差額・「案件を表示」ボタン
- 選択した差分を反映した場合の影響額を表示する: 売上 / 案件費用 / 粗利 / 経常利益の「確定値 → 反映後」
- 「選択した変更を反映」ボタンと「すべて反映」ボタン（確認ダイアログで影響額を再表示）。選択した明細だけ、確定明細を最新の値に置き換える（追加 → 確定明細に追加 / 削除 → 確定明細から削除 / 金額・区分変更 → 確定明細を更新）。反映の都度、反映者・反映日時を記録する（確定者・確定日時は保持）
- 反映・見送りの Server Action は選択された `(source_type, source_id)` と、画面で見ていたその明細の状態（在否・実績額・チーム・分類）を受け取る。値はサーバ側でライブ集計し直したものを使い（クライアントから送られた金額は使わない）、画面で見ていた状態と現在の状態が食い違う（表示後にさらに変更された）明細があれば「再読み込みしてから操作してください」として拒否する（利用者が見ていない変更を反映・見送りしない）
- 未処理の差分がなくなるとアラートが消え、確定情報に「最終反映: 日時 反映者」を併記する

**見送り（明細単位）**

- 「選択した変更を見送る」ボタン（確認ダイアログあり）。見送った差分は確定明細を変えずにアラート・件数から外す
- 見送りは **その時点の変更内容**（ライブの在否・実績額・チーム・分類）に対して行う。見送り後に同じ明細がさらに変更された場合は、再び未処理の差分としてアラートに出す
- 見送った差分は差分一覧の下の「見送り済み」（折りたたみ）に、見送った日時・見送った人とともに表示する。そこから「見送りを取り消す」（未処理に戻す）・「選択した変更を反映」もできる
- 見送り記録は、その明細を反映したとき・「確定済み」をオフにしたとき（CASCADE）・確定直後の取り直しで削除する。差分が解消した（元データが確定値と同じに戻った）明細の見送り記録は表示しない

**担当者への注意表示（案件詳細モーダル）**

- 案件の作成・編集時、その案件が確定済みの月に計上される場合は「この案件は確定済みの月（YYYY年M月）の損益計算書に計上されています。変更は経理の確認後に損益計算書へ反映されます」と表示する（保存は妨げない）。下書き（新規作成を含む）は計上されていないため「この案件の開始日は損益計算書で確定済みの月（YYYY年M月）です。経理申請すると、経理の確認後にその月の損益計算書へ反映されます」と表示する
  - 判定は保存済みの開始日・入力中の開始日のどちらかの月が確定済みであるとき（開始日を確定済みの月へ / から変更する場合も含む）
  - 対象: 担当者の案件詳細モーダル（新規作成を含む）、経理用の案件詳細モーダル（下書きに戻す操作を含む）
  - 確定済みの月の一覧は profit_loss_closings の SELECT（ログインユーザー全員に許可）から取得する

**チームリーダー**: アラート・差分一覧・反映 / 見送り操作は表示しない（確定値のみ表示。見送り記録は RLS でも読めず、反映・見送りも拒否される）

#### 4.16.8 画面

- 損益計算書画面 (/profit-loss)

### 4.17 年間推移表示 (F018)

#### 4.17.1 概要

- 年度（**7月〜翌6月**）を選択すると、12ヶ月分の損益推移を一覧表示する
- 「2026年度」= 2026年7月〜2027年6月
- 列: 7月〜翌6月の12ヶ月＋年度合計、行: 売上 / 案件費用 / 粗利 / 管理費 / 経常利益
- 年度の全期間を 1 回のクエリで取得し、サーバ関数内で月別にバケット分けする
- PostgREST は 1 リクエストの行数を max_rows（既定 1000。埋め込みリソースの配列にも掛かる）で打ち切るため、集計元の取得は id のキーセット方式（id > 直前の最大 id）でページングして全件を集める（`fetchAllPages`。通常は 1 ページ = 1 往復。offset 方式と違い、取得中に前の行が削除されても読み飛ばさない）。確定明細・見送り記録も埋め込まずに別クエリでページングする
- 確定済みの月（[4.16.7](#4167-月次収支確定issue-148)）は確定明細（スナップショット）から集計し、列見出しに鍵アイコンを付ける（確定後に未処理の変更がある月はアラートアイコン。経理担当者・管理者のみ）。確定ヘッダ＋明細＋見送り記録も取得範囲で 1 回に取得し、同じ `Promise.all` に含める
- 確定後の変更のバナー用の集計（未処理の差分がある月と件数）は、確定済みの月の一覧を取得したうえで、連続する確定済みの月ごと（通常は 1 つの範囲）にライブ明細・確定明細・見送り記録を並列に取得し、月別に差分を数える（離れた確定済みの月の間にある未確定の月の行は取得しない）。年間推移では差分を計算しない（件数はこの集計から表示する）。月次収支の確定はライブ集計に必要な行（案件の売上・費用、定期費用、経理追加収支、損益調整）だけを取得する。月次タブの差分一覧で追加・削除の差分があるときのみ、移動元・移動先の月の判定のために ID 指定の補完取得を 1 往復行う
- 取得範囲の絞り込み（Issue #16）：月次は対象月＋月未確定（NULL）行のみ、年間推移は年度 12 ヶ月＋月未確定（NULL）行のみを取得する。案件の売上・費用（`business` / `costs`）は埋め込みリソース `matters!inner` 側に「下書きでない AND（`start_date` が期間内 OR NULL）」（`matterPeriodFilter`。`referencedTable: "matters"` の `or()` 1 つにまとめる）、`extra_entries.entry_date` は「期間内 OR NULL」、定期費用は適用期間の重なり（`start_month < 翌月1日 AND (end_month IS NULL OR end_month >= 当月1日)`）で絞り、支払サイクルの計上判定は集計側で行う。損益調整は `target_month` の範囲で絞る（NOT NULL）。いずれも 5 テーブルの一括取得（`Promise.all`）のままで、年間推移が月単位の 12 回クエリにならない。範囲境界の単一の定義は `reportRangeBounds`（`app/utils/profitLossLogic.ts`）。月次では対象行が取得期間外へ移動した調整（`orphanedAdjustments`）のラベル解決用に、欠けている対象行だけを ID 指定（`in()`）で補完取得する（通常は 0 件で追加クエリなし、あっても `Promise.all` で 1 往復にまとめる。補完行は月振り分けで集計から除外されるため集計値は不変。年間推移は対象外で往復を増やさない）

#### 4.17.2 画面

- 損益計算書画面 (/profit-loss) 内のタブ切替で表示

### 4.18 定期費用マスタ管理 (F019)

#### 4.18.1 概要

- 定期的にかかる管理費（家賃・システム利用料など）を登録・管理する
- 支払サイクル（月払い / 四半期払い / 年払い）に対応し、支払月の損益計算書に支払額が全額算入される
- 実レコードは生成しない（適用期間と支払サイクルから計算で算出するため、登録・変更が即座に全期間へ反映される）

#### 4.18.2 登録項目

| 項目          | 説明                                               | 必須 |
| ------------- | -------------------------------------------------- | ---- |
| 名称          | 例: オフィス家賃                                   | ○    |
| 品目          | 品目マスタ（select_options の item）から選択       | ○    |
| 支払額（1回） | 円。支払サイクル1回あたりの金額（年払いなら年額）  | ○    |
| 支払サイクル  | 月払い / 四半期払い / 年払い（既定: 月払い）       | ○    |
| チーム        | チームマスタから選択。未選択 = 「全体共通」        | -    |
| 適用開始月    | 最初の支払月。以降はサイクル間隔ごとに支払月となる | ○    |
| 適用終了月    | この月まで損益に算入する（含む）。未設定 = 継続中  | -    |
| コメント      | 備考                                               | -    |

#### 4.18.3 機能

- 定期費用一覧表示・追加・編集・削除
- 一括保存（マスタデータ管理と同じステージング編集方式）

#### 4.18.4 金額改定の運用

月額が改定された場合は、既存行の適用終了月を改定前月に設定して打ち切り、新しい金額の行を改定月から新規登録する。これにより過去の月の損益計算書が遡って変わることを防ぐ。

損益計算書で確定済みの月（[4.16.7](#4167-月次収支確定issue-148)）がある場合も定期費用マスタは編集できるが、確定済みの月の損益計算書（確定値）には反映されず、変更アラートも出さない。適用期間に確定済みの月が含まれる行には「確定済みの月（YYYY年M月〜）の損益計算書には反映されません」と注記する。反映したい場合は損益計算書でその月の「確定済み」をオフにしてから再度オンにする。

#### 4.18.5 画面

- 定期費用マスタ画面 (/recurring-costs)

### 4.19 経理追加収支管理 (F020)

#### 4.19.1 概要

- 損益計算書は案件管理と定期費用マスタのデータだけでは実際の収支と必ずしも一致しないため、案件に紐づかない収入・支出を経理担当者・管理者が自由に登録・編集できるようにする
- 収入エントリは「請求額 → 売上」「経費 → 費用」の両方を計上できる（例: 受託収入とその外注費をセットで記録）。支出エントリは経費のみを計上する
- 登録したエントリは日付（entry_date）の属する月の損益計算書に算入される。日付未入力は「月未確定」として別枠表示する
- マイナス金額を許容し、案件側のデータを直さずに損益計算書上で差異の減額調整ができる（互換性のため残すが、**案件・定期費用マスタに紐づく差異は損益調整（[4.16.5](#4165-損益調整実績額修正)）で扱い、それらに紐づかない収入・支出のみ本機能で扱う**）

#### 4.19.2 登録項目

| 項目       | 説明                                                                               | 必須        |
| ---------- | ---------------------------------------------------------------------------------- | ----------- |
| 種別       | 収入 / 支出                                                                        | ○           |
| 分類       | 収入時は収入分類マスタ、支出時は支出分類マスタから選択（種別で選択肢が切り替わる） | ○           |
| 日付       | カレンダー入力。損益計算書に算入する月の判定に使用。未入力 = 月未確定              | -           |
| 請求書番号 | 自由入力。**収入時のみ**                                                           | -           |
| 内容       | 自由入力。過去に入力した値をサジェスト表示する                                     | ○           |
| 請求先     | 自由入力。過去に入力した値をサジェスト表示する。**収入時のみ**                     | -           |
| 責任者     | メンバー（profiles）から選択                                                       | ○           |
| チーム     | チームマスタから選択。未選択 = 「全体共通」                                        | -           |
| 請求額     | 円・税別。マイナス可・0 不可。**収入時のみ**                                       | ○（収入時） |
| 経費       | 円・税別。マイナス可・0 不可。収入時は任意（収入に紐づく経費）、支出時は必須       | ○（支出時） |
| 決済方法   | 決済方法マスタから選択。**支出時のみ**                                             | ○（支出時） |

#### 4.19.3 機能

- 経理追加収支画面（/extra-entries）で一覧表示・追加・編集・削除（ステージング編集方式・一括保存。マスタデータ管理・定期費用マスタと同方式）
- 分類（収入分類 / 支出分類）・決済方法の選択肢は、マスタデータ管理（F016。管理画面 /dashboard）で編集する
- 内容・請求先の入力欄は、登録済みエントリの過去の入力値をサジェスト候補として表示する
- 編集は経理担当者・管理者のみ。チームリーダーには損益計算書上で明細の閲覧のみ許可する（自チーム向け＋全体共通）
- 損益計算書で確定済みの月（[4.16.7](#4167-月次収支確定issue-148)）のエントリは追加・編集・削除できず、確定済みの月へ / からの日付の変更もできない（入力欄・削除ボタンを無効化し、日付の選択肢から確定済みの月を除外する。保存時にサーバ側・DB の Row Level Security でも拒否する）。編集するには損益計算書で「確定済み」をオフにする。一括保存では、画面に読み込んだ時点と比べて追加・削除・編集した行だけを送る（編集していない行は更新しない）ため、確定済みの月のエントリがあっても他の月のエントリは保存でき、読み込み後に他の利用者が保存した内容を読み込み時点の値で上書きすることもない。編集した行が読み込み後に他の利用者に削除されていた場合は、何も保存せずに再読み込みを促す（削除した行が既に削除されていた場合は、その削除だけを省いて保存する）。保存（追加・更新・削除）は 1 トランザクションで行い、保存前の確認の後に月が確定されるなどで 1 件でも保存できなければ何も保存せずにエラーを表示する（一部だけ保存された状態は残らない）。保存時の必須・金額のチェックは送る行（追加・編集した行）だけに行う（編集していない行・確定済みの月でロックされた行の既存の値で保存が止まらない）
- **前月コピー**: 損益計算書画面（/profit-loss）の月次タブに「前月の経理追加収支をコピー」ボタンを置く（経理担当者・管理者のみ表示。RLS でも書き込みは同ロールに限定される）
  - 表示中の対象月の前月に entry_date が属する経理追加収支を取得し、entry_date を当月の同日（対象月にその日が無い場合＝月末超過は対象月の末日）に置き換えて当月分として一括登録する
  - 分類・内容・請求先・責任者・チーム・金額・決済方法を引き継ぐ。請求書番号は当月の値が別物のため常に空にする
  - 実行前に確認ダイアログでコピー件数・対象月を表示する。当月に既存の経理追加収支がある場合は追記になる旨を案内する
  - 前月分が 0 件のとき、表示中の月が確定済みのときはボタンを無効化する（確定済みの月へのコピーはサーバ側・RLS でも拒否する）
  - entry_date が NULL（月未確定）の明細はコピー対象外（前月の対象取得時点で範囲外になる）
  - 複製元は確認ダイアログの表示後、登録直前にサーバ側で id 指定により改めて取得する（確認から実行までの間の他利用者による編集・削除を反映するため）。当月に既に同一内容（種別・分類・内容・責任者・チーム・金額）の明細がある行は二重コピーとみなし登録をスキップする（確認ダイアログを見逃した連続実行の重複作成防止）
  - コピー後は経理追加収支・損益計算書のキャッシュを無効化し、画面へ即時反映する

#### 4.19.4 損益計算書への反映

- 収入エントリ: 請求額を売上合計へ、経費（入力時のみ）を案件費用合計へ算入
- 支出エントリ: 経費を案件費用合計（分類別）へ算入
- 分類別収支では、請求額・経費ともにエントリの分類（収入分類 / 支出分類）の行へ算入する（[4.16.2](#4162-計上ルール) の振り分けルール参照）。支出エントリは売上のない分類となるため、粗利がマイナスの行として表示される
- 案件別収支では、エントリのチームの配下の「経理追加収支（案件外）」行にまとめる（チーム未指定は「全体共通」グループ）
- 計上月は日付の属する月。日付未入力は「月未確定」として別枠集計する
- チーム別内訳にも算入する（チーム未指定は「全体共通」）
- 案件（business / costs）・定期費用マスタ（recurring_costs）に紐づく実績額の差異は経理追加収支ではなく損益調整（[4.16.5](#4165-損益調整実績額修正)）で扱う。前月の経理追加収支コピー（4.19.3）のコピー対象にも損益調整は含まれない（単月の差異は繰り越す性質のものではないため）

#### 4.19.5 画面

- 経理追加収支画面 (/extra-entries)
- 損益計算書画面 (/profit-loss) 内の経理追加収支セクション（明細表示）・経理マスタ系操作ボタン（管理リンク）

### 4.20 事前収支申告 (F021)

#### 4.20.1 概要

- 各チームのチームリーダーが、翌月のチーム収支（見込み収入・見込み支出）を明細付きで申告する
- 申告期限は毎月20日（当月20日までに翌月分を申告）。期限は未申告リマインドのトリガーであり、期限後の申告・修正も可能（DB / UI ではロックしない）
- 閲覧・編集はチームリーダー・経理担当者・管理者のみ。チームリーダーは自チーム分のみ
- 1 チーム × 1 対象月につき申告は 1 件（`budget_declarations` の UNIQUE 制約）。合計金額はヘッダに持たず明細から集計する

未申告チームへの Slack リマインドは [4.20.6](#4206-未申告-slack-リマインド) を、毎月固定の収入・支出を都度入力せず自動で明細に反映する「定期明細」は [4.20.7](#4207-定期明細毎月固定の収入支出) を参照。

#### 4.20.2 申告項目

| 項目         | 説明                                                                         | 必須 |
| ------------ | ---------------------------------------------------------------------------- | ---- |
| 対象月       | 申告対象の月（月初日で保持）。一覧の初期表示は翌月                           | ○    |
| チーム       | チームマスタの値。チームリーダーは自チームのみ                               | ○    |
| 申告者       | 最終更新したメンバー（`declared_by`）                                        | ○    |
| コメント     | 補足コメント（自由入力）                                                     | -    |
| 明細：種別   | 収入 / 支出                                                                  | ○    |
| 明細：分類   | 収入は案件分類マスタ、支出は品目マスタ                                       | ○    |
| 明細：内容   | 自由入力（例: ○○受託案件、外注費）                                           | ○    |
| 明細：金額   | 見込み金額（円・税別）。正の値のみ（符号は種別が決める）                     | ○    |
| 明細：担当者 | 収入・支出ごとの担当者（メンバー。全メンバーから選択、チーム所属で絞らない） | -    |

#### 4.20.3 一覧ビューの機能

- 対象月を月ピッカーで選択する。初期表示は JST 基準の翌月
- 対象月のチーム × 申告状況（申告済み / 未申告）を一覧表示する
  - チームリーダー: 自チームのみ。経理担当者・管理者: 全チーム
  - 未申告のチームも行として並べる（未申告の可視化が目的のため、申告のあるチームだけを並べない）
  - チームマスタから外れた（無効化・改名された）チームの申告も末尾に表示し、取りこぼさない
- 各行に収入合計・支出合計・差引（収入合計 − 支出合計）を表示し、表示中の行の合計を合計行に表示する
- 行を開くと申告明細（種別・分類・内容・金額・担当者）とコメントを参照表示する
  - 複数チームの明細を同時に開ける（1 チームずつではなく独立して開閉できる）
  - テーブル上部の「すべて開く」「すべて閉じる」で申告済みの全チームの明細を一括開閉できる（未申告チームは明細が無いため対象外）
  - 対象月を切り替えると開閉状態はリセットされる
- 申告者名・明細の担当者名は `profiles` の RLS で読めない場合に「-」表示となる（申告状況・集計はそのまま表示する）
- 各行に「申告する」（未申告）／「編集する」（申告済み）ボタンを表示し、作成・編集フォームを開く

#### 4.20.4 作成・編集・削除フォームの機能

- 一覧の行から作成・編集フォーム（モーダル）を開く。対象月は一覧で選択中の月に固定（フォーム内では変更不可）
- チーム
  - チームリーダー: 自チーム固定（選択不可）
  - 経理担当者・管理者: 選択可能。ただし編集時（既存の申告を開いた場合）は対象月・チームの組み合わせを変えないため、ロールに関わらず固定表示にする
  - 選択可能な場合にチームを変更すると、既に入力済みの明細行があれば「変更するとクリアされる」旨を確認のうえクリアする（前月コピーで別チームの明細一式を持ち込んだ状態のまま誤って別チームとして保存することを防ぐ）
- 明細行を動的に追加・削除できる。各行は種別（収入 / 支出）・分類・内容・金額・担当者を入力する
  - 分類の選択肢は種別に連動する（収入 = category、支出 = item の既存マスタを流用）。種別を変更すると分類は未選択に戻る
  - 担当者はメンバー（profiles）から選択する任意項目（NULL 許容）。選択肢は全メンバー（チーム所属で絞らない）。経理追加収支の責任者と同じ方式で、選択後にクリアもできる
- 新規作成フォームを開くと、対象月が適用期間内の定期明細（[4.20.7](#4207-定期明細毎月固定の収入支出)）があれば、明細行（担当者含む）として自動で展開表示される（バッジ「定期」を付けて区別する）。編集時（既存の申告を開いた場合）は展開しない（二重計上防止）。展開された行も他の行と同様に編集・削除してから保存できる
- 「前月の明細をコピー」ボタン（新規作成時のみ表示。編集時は対象外）で、対象月の前月・同チームの申告明細（種別・分類・内容・金額・担当者）を現在の明細行の末尾にまとめて取り込める（コメントは対象外。前月固有の内容の可能性が高いため）。定期明細の自動展開と前月コピーを両方使った場合の重複を避けるため、新規作成時の初期投入は定期明細を優先し、前月コピーは利用者の明示操作とする
  - 取り込んだ行は未保存の新規行として追加されるだけで、他の行と同様に編集・削除してから保存できる
  - 前月・同チームの申告が無い場合、または申告はあるが明細が0件の場合はボタンを無効化し、理由をツールチップで表示する。チームリーダーは自チームの前月申告しか読めない（他チームの前月申告は RLS 上そもそも存在しないものとして扱われ、コピーできない）
  - 既に明細行がある状態で押した場合は「追記しますか」の確認ダイアログを経てから追加する（重複防止）。明細 0 件の状態では確認なしで取り込む
  - 分類がマスタから消えている（無効化・改名された）前月明細を取り込んだ場合、値はそのまま保持して空欄に見せないが、そのまま保存はできない。分類 Select の選択肢にはラベルへ「（マスタ未登録）」と付記した選択肢を一時的に追加し、かつ選択不可（disabled）にする（新規行のドロップダウンからは選べない）。該当行には「マスタ未登録のため選び直してください」と表示し、フォーム上部にも「分類の見直しが必要です」の警告を出す。保存時は有効なマスタ値への選び直しが必須になる
- 収入合計・支出合計・差引（収支）をフォーム内にリアルタイム表示する（保存前の集計は `summarizeBudgetItems` を流用）
- 保存前にバリデーションを行い、不備があれば保存を中止して案内を表示する
  - 対象月・チームが未設定（通常は発生しない。表示上の防御）
  - 明細の種別・分類・内容のいずれかが未入力
  - 明細の金額が0以下
  - 明細の分類がマスタ（収入 = category、支出 = item）に登録されていない（前月コピー・定期明細の自動展開で持ち込んだ無効値、および無効化後に選び直した値を含む）
  - 明細 0 件（コメントのみ）は許容する
- 保存は確認ダイアログを経てから実行する。Server Action（`saveBudgetDeclaration`）は DB 関数 `save_budget_declaration`（`docs/database.md` 5.9）を1回呼ぶだけで完結し、「ヘッダの作成/更新（作成は INSERT、編集は UPDATE）+ 明細の差し替え（既存明細を全削除して入力内容を登録し直す）」を単一トランザクションで行う（途中で失敗した場合は保存前の状態に完全にロールバックされる）。保存直前にサーバ側で最新の分類マスタ（`category` / `item` の有効値）と照合し、マスタ未登録の分類が残っていれば保存を中止する（クライアントのマスタ表示に依存せず、直接の Server Action 呼び出しによる回避も防ぐ。担当者の `validateMemberIds` と同じ方式）
  - 新規作成が `(target_month, team)` の一意制約に違反した場合（既に他の担当者が作成済み）は、その旨を案内して保存を中止する（一覧から編集するよう促す）
- 削除は編集フォームからのみ行える。確認ダイアログの上で `deleteBudgetDeclaration` を呼び、ヘッダを削除する（明細は `ON DELETE CASCADE` で同時に削除される）
- 期限（毎月20日）を過ぎても作成・編集・削除は常に可能（DB / UI ではロックしない。仕様どおり）
- 書き込み権限（チームの判定）は RLS が最終防御だが、フォーム表示・Server Action の双方で `canWriteBudgetTeam` により事前チェックし、権限不足を分かりやすいメッセージで案内する

#### 4.20.6 未申告 Slack リマインド

- Vercel Cron が毎日 09:00 JST（`0 0 * * *` UTC）に `app/api/cron/budget-declaration-reminder/route.ts`（Route Handler）を実行する（`vercel.json`）
- `Authorization: Bearer ${CRON_SECRET}` を検証し、一致しない場合は 401 を返す
- リマインド対象日は `budget_declaration_reminder_settings` テーブル（1 行のみ。[database.md 3.11](database.md#311-budget_declaration_reminder_settings-テーブル)）の `target_days` で管理し、デプロイなしで編集できる。DB 取得に失敗した場合は `DEFAULT_BUDGET_DECLARATION_REMINDER_TARGET_DAYS`（`[15, 18, 20]`）にフォールバックする（`getBudgetDeclarationReminderTargetDays`）
- 対象日の編集 UI は `/budget-declarations` の「リマインド設定」セクション（admin / accounting のみ表示。[5.3.14](#5314-事前収支申告画面-s014)）から行う。対象日（1〜31）を複数選択して保存すると `updateBudgetDeclarationReminderTargetDays` が `id = 1` の既存行を UPDATE する（INSERT / DELETE は不可）。対象日を空にして保存するとリマインドが停止し（cron は動作するが送信されない）、UI 上に警告を表示する
- JST の「今日」が対象日リストに含まれていなければ何もしない（対象日以外は 200 でスキップを返す）。**対象日リストを空にするとリマインド自体が停止する**（cron は動作するが常にスキップ）
- 対象日であれば、対象月（JST の翌月。一覧の初期表示と同じ `defaultTargetMonth`）について以下を行う
  1. 有効な team 選択肢（チームマスタ）から全チームを取得する
  2. 翌月分の `budget_declarations` が存在しないチームを抽出する（`undeclaredBudgetTeams`）。未申告チームが 0 件なら通知しない
  3. 未申告チームのチームリーダー（`profiles.class = 'teamleader' AND team = 対象チーム`）の `slack_id` を取得する。`slack_id` 未設定のリーダーやリーダー不在のチームはメンションなしでチーム名のみ通知する（`groupSlackIdsByTeam`）
  4. チームごとに `<@slack_id>` メンション（複数リーダーがいれば全員分）+ チーム名を並べ、期限（毎月20日）と申告ページ URL を添えた 1 通のメッセージを組み立て（`buildBudgetDeclarationReminderMessage`）、`SLACK_WEBHOOK_URL` に送信する
- cron ハンドラは認証セッション（cookie）を持たないため、`app/utils/supabase/budgetDeclarationReminderData.ts` に限り `SUPABASE_SERVICE_ROLE_KEY`（RLS を完全にバイパスできる強力な権限を持つキー）を用いた server-only なクライアントで参照する。アプリ側の利用は読み取りのみ・このモジュール限定に絞っているが、キー自体の権限がそれに限定されるわけではないため、キーはクライアントへ露出させない
- 申告ページ URL は Vercel が自動設定する `VERCEL_PROJECT_PRODUCTION_URL` / `VERCEL_URL` から組み立てる（追加の環境変数は不要）
- 対象日・未申告チーム抽出・メッセージ生成は副作用のない純粋関数（`app/utils/budgetDeclarationReminder.ts`）に切り出し、ユニットテストする（TZ=Asia/Tokyo 固定）

#### 4.20.7 定期明細（毎月固定の収入・支出）

- 毎月同額で発生する収入・支出（例: 保守契約の月額収入、固定の外注費・ツール利用料）を一度登録すれば、以降の月の新規申告作成時に自動で明細として載る（Issue #109）。定期費用マスタ（[4.18 定期費用マスタ管理 (F019)](#418-定期費用マスタ管理-f019)）と同様の考え方だが、対象は事前収支申告の明細であり、テーブルも別（`budget_recurring_items`。[database.md 3.12](database.md#312-budget_recurring_items-テーブル)）
- **登録項目**: チーム（チームリーダーは自チーム固定）/ 種別（収入・支出）/ 分類（種別連動。既存マスタを流用）/ 内容 / 金額 / 担当者（メンバー選択・任意） / 適用開始月 / 適用終了月（NULL = 継続中。クリアで継続中に戻せる）
- **反映方式**: 集計時に合算するのではなく、**申告作成時に明細として展開する**方式を採用した（案 A で確定）。新規申告フォームを開いたとき、対象月が適用期間内（`start_month <= 対象月 <= end_month` または `end_month` が NULL）の定期明細を初期明細として自動投入する。投入された行は保存すると通常の `budget_declaration_items` になり、以降は申告ごとに個別に編集・削除できる（定期明細マスタ自体は変更されない）
  - この方式により、既存の一覧・集計・Slack リマインドのロジックは変更不要になる（「申告済み / 未申告」の判定も定期明細の有無に影響されない）
  - （不採用案）集計時に定期明細を合算する方式は、未申告チームでも定期分が金額に載ってしまい「未申告」の意味が変わるため採用しなかった
- **既存申告の編集時には展開しない**（二重計上防止）。展開は新規作成フォームを開いたときのみ発生する
- 「前月の明細をコピー」（[4.20.4](#4204-作成編集削除フォームの機能)）と併用したときの重複を避けるため、新規作成時の初期投入は定期明細を優先し、前月コピーは利用者の明示操作とする
- 適用終了月を過ぎた定期明細は、それ以降の対象月の新規申告には展開されない
- 金額改定は定期費用マスタと同じ運用（既存行の適用終了月を設定して打ち切り、新しい行を追加する）とする
- 分類がマスタから消えている（無効化・改名された）既存行は、空欄に見せないよう「（マスタ未登録）」付き・選択不可で表示し、警告を出す。保存時は有効なマスタ値への選び直しが必須であり、サーバ側（`bulkSaveBudgetRecurringItems`）でも最新の分類マスタと照合する。無効値のまま残すと以降の新規申告へ自動展開され続けるため、無効化後は速やかに選び直す
- 管理画面（定期明細画面 /budget-declarations/recurring）はチームリーダー・経理担当者・管理者がアクセスでき、チームリーダーは自チームの、経理担当者・管理者は全チームの定期明細を登録・編集・削除できる（UI と RLS の両方で担保。[database.md 5.11](database.md#511-budget_recurring_items-テーブル)）。定期費用マスタ画面と同じステージング編集（画面上でまとめて追加・編集・削除してから一括保存）方式を採る

- URL: /profit-loss
- 構成要素

  - 経理マスタ系操作ボタン（経理担当者・管理者のみ）: 定期費用マスタ（/recurring-costs）・経理追加収支（/extra-entries）へのボタン
  - 確定後の変更の警告バナー（経理担当者・管理者のみ。未処理の変更がある確定済みの月と件数。月名で月次タブのその月へ切り替え。[4.16.7](#4167-月次収支確定issue-148)）
  - タブ切替（月次 / 年間推移）
  - 【月次タブ】
    - 対象月選択（月ピッカー、初期値は当月。確定済みの月は下線、未処理の変更がある月は強調表示）
    - 確定情報（確定済みの月は「確定済み」バッジ・確定日時・確定者・最終反映）と「確定済み」スイッチ（経理担当者・管理者のみ操作可。[4.16.7](#4167-月次収支確定issue-148)）
    - 「前月の経理追加収支をコピー」ボタン（経理担当者・管理者のみ。前月分が 0 件のとき・確定済みの月は無効化）
    - 確定後の変更の警告と差分一覧（確定済みで差分がある月・経理担当者・管理者のみ。選択チェック・影響額・「選択した変更を反映」「すべて反映」「選択した変更を見送る」、折りたたみの「見送り済み」一覧と「見送りを取り消す」）
    - サマリーカード（売上 / 案件費用 / 粗利 / 管理費 / 経常利益）
    - 案件別収支テーブル（チーム → 案件 → 案件内訳の 3 階層の展開。列: 売上 / 案件費用 / 粗利）
      - チーム行（小計）→ 案件行（案件 ID・案件名・分類バッジ・「案件を表示」ボタン）→ 案件内訳（売上明細・費用明細。「調整あり」バッジ・元データ変更の警告アイコン・「実績額を修正」操作（経理担当者・管理者のみ。明細行ごとにモーダルで実績額・調整理由を入力））
      - 案件行・明細行のタイトル横の編集アイコン（経理担当者・管理者のみ。[4.16.6](#4166-表示タイトルの変更issue-150)）と、上書き中の「名称変更」バッジ（元の名称をツールチップ表示）
      - 各チームの「経理追加収支（案件外）」行（展開で内容）、チーム未指定の経理追加収支は「全体共通」グループ
      - 確定後に未処理の変更がある案件行・明細行の変更アイコン（経理担当者・管理者のみ）
      - 合計行
    - 分類別収支テーブル（列: 売上 / 案件費用 / 粗利。粗利の降順。合計行あり）
    - 損益計算書テーブル（粗利 → 管理費 → 経常利益）
      - 売上総利益（粗利）（「売上 − 案件費用」を併記）
      - 管理費合計（費目別内訳・展開で定期費用明細。明細行は「元データ／調整／実績」の3列と「実績額を修正」操作・タイトルの編集アイコン（経理担当者・管理者のみ））
      - 経常利益（太字、マイナスは赤字）
    - 対象行が当月に存在しない損益調整の警告と削除操作（経理担当者・管理者のみ。該当がある場合のみ表示）
    - 経理追加収支セクション（選択月の明細一覧。0件の月は非表示）
    - チーム別内訳テーブル（経理担当者・管理者のみ。列: 売上 / 案件費用 / 粗利 / 管理費 / 経常利益）
    - 全体共通の管理費・経理追加収支（参考）セクション（チームリーダーのみ）
    - 月未確定の注記（該当データがある場合のみ）
    - 案件詳細モーダル（閲覧専用。「案件を表示」ボタンから起動）
  - 【年間推移タブ】
    - 年度選択（7月始まり）
    - 推移テーブル（列: 7月〜翌6月＋年度合計、行: 売上 / 案件費用 / 粗利 / 管理費 / 経常利益。横スクロール対応。確定済みの月は列見出しに鍵アイコン、確定後に未処理の変更がある月はアラートアイコン）

    - 収入追加ボタン
  - 支出エントリリスト（ステージング編集方式・一括保存）
    - 分類（支出分類） / 日付（カレンダー入力・クリア可） / 内容（サジェスト付き） / 責任者（メンバー選択） / チーム（選択。「全体共通」あり） / 経費（税別） / 決済方法 / 削除ボタン

  - 「前月の経理追加収支をコピー」ボタンは損益計算書画面（/profit-loss）の月次タブ側に置く（[5.3.10](#5310-損益計算書画面-s010) 参照）。本画面には置かない
- 日付のカレンダーはポータル表示とし、テーブルの横スクロール領域にクリップされないようにする

#### 5.3.14 事前収支申告画面 (S014)

- URL: /budget-declarations
- 構成要素
  - ページタイトル「事前収支申告」
  - リマインド設定セクション（admin / accounting のみ表示。teamleader / public には描画しない）
    - 対象日（1〜31）を選択する Chip 群（複数選択）と保存ボタン
    - 対象日が 0 件のときは「現在リマインドは無効です」の警告を表示する
    - 29〜31日は月によって存在しない旨の注記を表示する
    - 保存は確認ダイアログを経てから実行する（対象日を空にする場合はリマインド停止になる旨を案内する）
  - 「定期明細を管理」ボタン（S016 定期明細画面へ遷移）
  - 対象月ピッカー（初期値は翌月）
  - チーム別申告状況テーブル
    - チーム / 申告状況（申告済み・未申告バッジ） / 収入合計 / 支出合計 / 差引 / 申告者 / 最終更新 / 明細表示ボタン / 操作ボタン
    - 未申告のチームは金額欄を「-」とし、明細表示ボタンを無効化する
    - 差引がマイナスの行は金額を赤字で表示する
    - 合計行に表示中のチームの収入合計・支出合計・差引を表示する
    - 操作ボタンは未申告なら「申告する」、申告済みなら「編集する」と表示し、S015 のフォームモーダルを開く
    - テーブル上部に「すべて開く」「すべて閉じる」ボタンを表示する（申告済みチームが対象。0 件のときは「すべて開く」を無効化する）
  - 明細パネル（行を開いたときのみ取得・表示。複数チームを同時に開ける）
    - 種別 / 分類 / 内容 / 金額 / 担当者、コメント（参照のみ）
    - 明細が 0 件の申告でもコメントは表示する（DB は明細 0 件のヘッダを許容する）

#### 5.3.15 事前収支申告フォームモーダル (S015)

- 構成要素
  - 対象月（固定表示）・チーム（Select。チームリーダーは固定、経理・管理者は選択可。編集時は常に固定）

## 8. セキュリティ設計

### 8.1 認証

- Supabase Auth を使用した Google OAuth 認証
- 未来技術推進協会のドメイン(`future-tech-association.org`)のみログイン可能
- ミドルウェアによる保護されたルートの制御
  - /, /matters: 認証済みユーザーのみアクセス可能
  - /matters/team: チームリーダー・管理者のみアクセス可能
  - /matters/accounting: 経理担当者・管理者のみアクセス可能
  - /team, /accounting: 旧 URL。ロール保護は /matters/team, /matters/accounting と同じ（新 URL へのリダイレクト前に判定する）
  - /dashboard: 管理者のみアクセス可能
  - /profit-loss: チームリーダー・経理担当者・管理者のみアクセス可能
  - /recurring-costs: 経理担当者・管理者のみアクセス可能
  - /extra-entries: 経理担当者・管理者のみアクセス可能
- Supabase Auth 側の一時的障害（到達不能・5xx）では未ログイン扱い（/login への転送）にせず、503（`Retry-After: 2` 付き）を返す。Auth への 1 リクエストは 5 秒、`getUser()` 全体は 6 秒で打ち切る。後続の profiles 取得（再試行なし・5 秒で外側からも打ち切り）との合算でも約 11 秒のため、Vercel の 25 秒制限による 504 にならない。profiles 取得自体のタイムアウト超過も 503 に落ちる（それ以外の取得失敗は既存どおり `/` へ転送する）
- 既知の制約：Supabase Auth が「落ちている」のではなく「遅い」場合（Pause 解除直後の初回応答等）、期限切れトークンのリフレッシュ応答がタイムアウトに掛かると 503 になる。サーバ側でローテーション済みの旧リフレッシュトークンは再利用猶予（約 10 秒）後に失効するため、猶予を過ぎて再読込すると 400（非 retryable）でセッション破棄→ `/login` 転送になる。`Retry-After` に従い速やかに再試行すれば再ログインは不要なことが多い

### 8.2 認可

- Row Level Security (RLS)によるデータアクセス制御
  - 一般ユーザー: 自身の案件のみアクセス可能
  - チームリーダー: 自分のチームの案件にアクセス可能
  - 経理担当者: 全案件のアクセス・更新が可能
  - 管理者: 全データのアクセス・更新・削除が可能
- ユーザー権限に基づく UI 制御
  - ナビゲーションメニューの表示/非表示
  - トップページのハブカードの表示/非表示（権限のないページは出さない）
  - 操作ボタンの表示/非表示

### 8.3 セキュアな通信

- HTTPS 通信のみ使用
- 環境変数による機密情報の保護
  - SLACK_WEBHOOK_URL: Slack 通知用 Webhook URL
  - CRON_SECRET: Vercel Cron ルート（未申告 Slack リマインド）の認証用シークレット。`Authorization: Bearer` ヘッダで照合し、不一致は 401
  - SUPABASE_SERVICE_ROLE_KEY: RLS を完全にバイパスできる強力な権限を持つキー。本アプリでは cron ルート限定・読み取り専用の参照にのみ使用しているが、キー自体の権限を絞るものではないため、クライアントには露出させない

### 11.2 未申告 Slack リマインド（事前収支申告）

詳細は [4.20.6](#4206-未申告-slack-リマインド) を参照。

- Vercel Cron（毎日 09:00 JST）が `app/api/cron/budget-declaration-reminder/route.ts` を起動
- `budget_declaration_reminder_settings.target_days`（DB。空にすると停止可能）で指定した対象日にのみ、翌月分が未申告のチームへ 1 通のメッセージで通知
- 送信フロー
  1. Vercel Cron が `Authorization: Bearer ${CRON_SECRET}` 付きでリクエスト
  2. `SUPABASE_SERVICE_ROLE_KEY` の server-only クライアントでリマインド対象日設定・チームマスタ・申告状況・チームリーダーの `slack_id` を取得
  3. `buildBudgetDeclarationReminderMessage` でメッセージを組み立て、`SLACK_WEBHOOK_URL` に POST リクエスト
  4. 未申告チームが無い（全チーム申告済み）場合や対象日以外は送信しない
