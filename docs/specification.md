# 機能設計書

未来技術推進協会の経理システム（案件処理・経理処理）。本書は業務ルール・権限の意図・運用上の落とし穴のみを記す。アーキテクチャ・状態管理は `CLAUDE.md`（AI 向けの要約）、テーブル / RLS / トリガーは [database.md](database.md)、画面項目・関数はコードを正とする。

## 1. ロール

`profiles.class`（public / accounting / admin の 3 値）に格納する。チームリーダーは `class` の値ではなく `profiles.is_teamleader` フラグで表し、経理担当者・管理者と兼任できる。権限判定は「有効ロール集合 = `class` ＋（`is_teamleader` なら teamleader）」で行い（`effectiveRoles`）、いずれかのロールに許可があればアクセスできる。閲覧可能ルートは `app/utils/permissions.ts` の `ROUTE_PERMISSIONS` が単一の定義。

| ロール     | 意図                                                                                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| public     | 一般メンバー。自分の案件のみ操作できる                                                                                                                                                            |
| teamleader | （`is_teamleader` フラグ。`class` は public / accounting / admin のいずれでもよい）自チームの案件を閲覧できる（編集不可）。損益計算書は全チーム、事前収支申告は全チームを閲覧・自チーム分のみ編集 |
| accounting | 経理担当者。全案件の確認・完了処理、経理マスタ系（定期費用・経理追加収支・損益調整・月次確定）の編集                                                                                              |
| admin      | 全機能。ユーザー管理・項目管理は admin のみ                                                                                                                                                       |

- 認証は Google OAuth。`future-tech-association.org` ドメインのみログインできる。初回ログイン時に `profiles` へ自動登録する。

## 2. 案件の状態

下書き → 経理申請中（`is_fixed`）→ 経理確認完了（`is_completed`）。

- 経理申請後も担当者は編集できる。編集すると `has_updates` が立ち、経理用一覧でハイライト（「更」）される（差し戻し検知）
- 経理は完了案件を「経理申請中に戻す」、通知した案件を「下書きに戻す」ことができる
- 下書きは損益計算書に計上されない（[4.16.2](#4162-計上ルール)）
- 案件の削除は経理申請前のみ。案件・取引先・コストをまとめて削除する

## 3. 認可・セキュリティ

- 保護ルートの判定は middleware（`ROUTE_PERMISSIONS`）。データ側は RLS が最終防御で、UI の表示制御は補助
- チームリーダーは RLS 上、全チームの案件・売上・費用・定期費用・経理追加収支・損益調整・表示タイトル・確定明細を閲覧できる（損益計算書で他チームと比較するため。migration 40）。書き込み権限は変わらない（案件は所有者・経理担当者・管理者、調整・タイトル・確定は経理担当者・管理者）。画面上の案件一覧は `/matters`（自分の案件）・`/matters/team`（自チーム）で明示的に絞る
- `/matters` 自体はロール制限なし（ログイン必須）。`/matters/team`（teamleader・admin）・`/matters/accounting`（accounting・admin）・`/dashboard` 配下（admin）・`/profit-loss`（teamleader 以上）・`/recurring-costs` `/extra-entries`（accounting・admin）・`/budget-declarations`（teamleader 以上）にはロール制限がある。旧 URL `/team` `/accounting` は新 URL へのリダイレクト用で、リダイレクト前のロール保護のため同じ制限を持つ
- 制限ルートのロールは、検証済み JWT の `user_class` クレームと `user_is_teamleader` クレーム（Custom Access Token Hook が付与。[database.md 7 章](database.md)）から読み、DB クエリを避ける。どちらかのクレームが無効（`user_class` は欠落・`null`・空文字・文字列以外、`user_is_teamleader` は欠落・`null`・boolean 以外）なら `profiles` を DB 参照する（フック未有効化でも動くフェイルセーフ。新規ユーザーの初回トークンは必ず `null`）。認証の可否は `getUser()`（サーバ検証）で判定し、署名検証のない `getSession()` は使わない
- Supabase Auth 側の一時的障害（到達不能・5xx）では `/login` へ飛ばさず 503（`Retry-After: 2`）を返す（障害と偽造トークンを区別するため）。Edge の 25 秒制限に掛からないよう、Supabase への 1 リクエストは 5 秒、`getUser()` 全体は 6 秒、`profiles` 取得は内側 5 秒 / 外側 6 秒（外側 > 内側）で打ち切る。`profiles` のそれ以外の取得失敗は `/` へ戻す
- 既知の制約: Auth が落ちているのではなく遅い場合（Pause 解除直後の初回応答など）、期限切れトークンのリフレッシュ応答がタイムアウトすると 503 になる。サーバ側でローテーション済みの旧リフレッシュトークンは再利用猶予（約 10 秒）後に失効するため、猶予を過ぎて再読込すると 400 でセッション破棄 → `/login` になる。`Retry-After` に従って速やかに再試行すれば再ログインは不要なことが多い

## 4. 機能詳細

### 4.1 ユーザー認証 (F001)

[1](#1-ロール) を参照。画面は `/login`。

### 4.2 案件一覧表示 (F002)

- 自分の案件を状態（下書き / 経理申請中 / 経理確認完了）で色分けして表示する。カード / テーブルを切り替えられる
- 一覧のページネーションはクライアント側で行う（自分の案件・チーム案件・経理用一覧共通。既定 24 件/ページ、12/24/48/96 切替）。フィルタ変更時は 1 ページ目に戻る。チェック選択はページをまたいで保持され、完了・通知の対象になる（対象外になるのはサーバ側の絞り込みで非表示の分のみ）。サーバ側の絞り込み・ソートは変えない
- 案件の作成・コピーは案件詳細モーダルと同一コンポーネント（新規作成表示）で行う。作成後は一覧に即時反映される

### 4.3 案件登録 (F003)

- `/matters` の「+ 新規作成」から開くモーダル。基本情報・取引先（複数）・コスト（複数）を一括登録する。下書き保存 / 経理申請を選べる
- 案件開始日は必須（新規作成時）で、損益計算書の計上月に使われる。入力欄にその旨のヘルプを出す

### 4.4 案件詳細表示・編集 (F004)

- 取引先（報酬額・請求日・振込期限）・コスト（品目・支払い先・金額・支払い期限・通知方法・源泉徴収）を複数持つ
- 案件開始日は損益計算書の計上月を決める。案件の売上・費用はすべて開始日の月に計上され、下書きの間は計上されない（[4.16.2](#4162-計上ルール)）。開始日が損益計算書で確定済みの月に当たる案件の作成・編集時は、変更が経理の確認後に反映される旨を表示する（[4.16.7](#4167-月次収支確定)）
- 請求日は振込期限以前でなければならない（同日は可）
- チーム案件一覧（teamleader）からの詳細は閲覧のみ

### 4.5 案件削除 (F005)

[2](#2-案件の状態) を参照。確認ダイアログの後に削除する。

### 4.6 案件コピー (F006)

既存案件（基本情報・取引先・コスト。作成日時を除く）をコピーして新規作成モーダルを開く。タイトルに「(コピー)」を付ける。保存しなければ作成されない。

### 4.7 経理申請 (F007)

- `is_fixed` を true にする。売上金額（total_amount）が 0 の場合は警告して確認を求める
- 申請後も編集可能（[4.8](#48-経理申請後の案件編集-f008--案件更新の確認-f013)）

### 4.8 経理申請後の案件編集 (F008) / 案件更新の確認 (F013)

- 申請後に「更新」すると確認ダイアログを経て `has_updates` が true になる
- 経理は経理用一覧の「更」で更新された案件を識別する

### 4.9 関連案件管理 (F009)

長期案件の収支管理のため、案件に親案件を設定できる。親案件の詳細で子案件一覧と関連案件の収支合計を表示する。

### 4.10 チーム案件一覧 (F010)

- `/matters/team`。チームリーダーが自チームの案件（担当者・分類・請求額・コスト・状態）とチーム全体の収支を確認する。詳細は閲覧のみ

### 4.11 経理用案件一覧 (F011)

- `/matters/accounting`。全ユーザーの案件を表示する。案件の状態で色分けし、列ごとのフィルタを持つ。申請後に更新された案件はハイライトする
- 完了案件はデフォルトで非表示にしない（完了案件の確認も用途に含むため。未完了を先頭に寄せる並び順で対応し、件数対策はページネーションで行う）
- 未払いコスト数を表示する

### 4.12 案件確認・完了処理 (F012)

- 経理用案件詳細モーダルで取引先の確認完了・コストの支払い完了をチェックし、経理メモを追加して保存 / 完了する（確認ダイアログあり。`is_completed` を更新）
- 完了案件は「経理申請中に戻す」ことができる。案件が損益計算書で確定済みの月に計上される場合は、下書きに戻す・申請中に戻す操作の前に注意を表示する（[4.16.7](#4167-月次収支確定)）

### 4.13 Slack 通知 (F014)

- 経理が経理用一覧で案件を選び「担当者に連絡」からメッセージを入力すると、選択した案件の担当者へ Slack で一括通知する（案件名・担当者名・メッセージ）
- 通知後、選択した案件は下書き状態に戻る
- 送信は `SLACK_WEBHOOK_URL`（環境変数）の Webhook への POST
- 定型文（ヘッダと本文テンプレート）は経理・管理者が経理用一覧の「通知設定」から編集できる（`slack_notification_settings`。[database.md 3.18](database.md)）。プレースホルダは `{matter}`（案件名）・`{assignee}`（担当者のメンション）・`{message}`（送信時に入力したメッセージ。本文に必須）・`{sender}`（送信者名）・`{datetime}`（送信日時）。ヘッダにはプレースホルダを使えない。未知のプレースホルダ・空・1000 文字超は保存できない。保存画面にサンプル値のプレビューを出す
- 定型文の取得に失敗した場合は従来の固定文で送る（通知を止めない）。送信者はセッションのプロフィールから取り、クライアントの指定は使わない
- 投稿チャンネルは画面から変更できない（Webhook で固定）。変更は Webhook を作り直して `SLACK_WEBHOOK_URL` を差し替える（[setup.md](setup.md)）

### 4.14 ユーザー管理 (F015)

admin のみ。画面は [5.3.9](#539-管理画面)。

- 権限（表示名はメンバー / 経理 / 管理者。必須。保存する値は public / accounting / admin）・チームリーダー（チェックボックス。`is_teamleader`。経理・管理者にも付けられる）・チーム・Slack ID を編集する。チームリーダーにチェックを入れたユーザーはチームが必須。読み込み時にチームリーダーだった行はチェックを外すとチームが空になり、チェックを読み込み時点の値に戻すとチームも読み込み時点の値に戻る（チームリーダーでなかった行は、チェックを付け外ししてもチームは変わらない）
- 一括保存: 「一括保存」を 1 回押すと、読み込み時点（または直前の保存成功時点）から変わった行だけを 1 回の RPC（`update_profiles`。[database.md 5.1](database.md#51-profiles-テーブル)）で保存する。1 件でも保存できなければ（管理者権限が外れた・ユーザーが削除された等）どの行も保存せず、編集内容は画面に残す。保存前にクライアント側で入力チェックし、確認ダイアログを出す
- 保存の Server Action（`bulkUpdateProfiles`）は RLS に加えて呼び出し元が admin であることを確認する（多層防御）。admin 以外は入力チェック・書き込みの前に権限エラーを返し、何も保存しない（RLS 上は書き込める自分の Slack ID もこの経路では変更できない）
- 一覧は権限ごとの見出し付きセクションに分けて表示する（詳細は [5.3.9](#539-管理画面)）。行（スマホはカード）の背景はチームごとに色分けし、変更した行は背景ではなく左端のオレンジの線と「変更あり」バッジで示す（チームの色と重ならないようにするため）
- 編集中は他の管理者の更新で画面を黙って上書きしない（未保存の変更が無くなった時点で最新の値に同期する）
- 既知の制約
  - 権限を変更しても、middleware が参照する JWT の `user_class` クレームには、対象ユーザーのトークンが更新される（最大約 1 時間後）か再ログインするまで反映されない（3 章参照）。`is_teamleader` を変更したときの JWT の `user_is_teamleader` クレームも同様
  - 未保存の変更の警告は、リロード・タブを閉じる操作（beforeunload）と、管理画面のサイドメニュー / タブ（ユーザー管理 ⇄ 項目管理）の切り替えだけが対象。ヘッダー・トップページのリンクやブラウザの「戻る」では確認せず、未保存の変更は破棄される

### 4.15 マスタデータ管理 (F016)

admin のみ。画面は [5.3.9](#539-管理画面)。選択肢（チーム / 分類 / 品目 / 収入分類 / 支出分類 / 決済方法）の追加・改名・削除（無効化）・ドラッグ&ドロップでの並べ替えを、カテゴリごとの「保存」で保存する（「変更を破棄」でそのカテゴリの未保存の変更を元に戻せる）。

- 項目名は種類ごとに一意（`UNIQUE(type_id, value)`）で、この制約は削除済み（無効化済み）の項目にもかかる。表示中の項目どうしで名前が重なる場合は保存しない
- 追加した項目名が削除済みの項目と同じ場合は、新しい行を作らずその項目を再び有効にする
- 追加した項目名が有効な項目と重なる場合、または既存の項目を削除済みの項目と同じ名前に改名する場合は保存できず、「同じ名前の項目が既にあります（削除済みの項目を含む）」と表示する
- 連鎖した改名（「P→Q」と「Q→R」を同じ保存で行う）はできる。2 つ以上の項目の名前を入れ替える（「P→Q」と「Q→P」。循環も同様）のは 1 回の保存ではできない（別の名前を経由して 2 回に分けて保存する）
- 保存で送るのは変更した既存の行と追加した行だけ（変更していない行は `updated_at` も変わらない）。UPDATE で更新できた行が 0 行だった場合（他の管理者が削除した、権限が無い等）は失敗として再読み込みを促す
- 保存が途中で失敗した場合は、保存できた行を保存済みとして扱い、保存できなかった変更だけを未保存として残す（保存し直しても登録済みの行を重複登録しない）
- 未保存の変更の警告の対象範囲は [4.14](#414-ユーザー管理-f015) と同じ

### 4.16 月次損益計算書表示 (F017)

#### 4.16.1 概要

月ごとに、スプレッドシート運用と同じ「粗利 → 管理費 → 経常利益」の構造で損益を表示する。

- **売上総利益（粗利） = 売上合計 − 案件費用合計** ＝ 案件の粗利 ＋ 経理追加収支（収入）の粗利（請求額 − 経費）
- **管理費合計 = 定期費用 ＋ 経理追加収支（支出）の経費**
- **経常利益 = 粗利合計 − 管理費合計**

#### 4.16.2 計上ルール

| 区分         | 計上月の判定                                                     | 金額                                                                             |
| ------------ | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 売上         | 所属案件の matters.start_date（案件開始日）の属する月            | business.amount                                                                  |
| 案件費用     | 所属案件の matters.start_date（案件開始日）の属する月            | costs.price                                                                      |
| 管理費       | 定期費用マスタの支払月（適用期間内かつ支払サイクルに一致する月） | recurring_costs.price（支払月に全額計上）                                        |
| 経理追加収支 | extra_entries.entry_date（日付）の属する月                       | 収入エントリの請求額は売上へ、経費は案件費用へ。支出エントリの経費は管理費へ算入 |

- 案件の売上・案件費用は、請求日（invoice_date）・支払い期限（period）に関わらず案件開始日の月に全額計上する（1 案件の収支を必ず同じ月に載せ、月次で案件単位の損益を読めるようにするため。数ヶ月にまたがる案件も開始月に全額）。invoice_date / period は損益の計上判定には使わない。過去の月にも遡って同じ基準を適用する
- **下書きの案件は計上しない**（`is_fixed = false` かつ `is_completed = false`。NULL は false 扱い）。月次・年間推移・月未確定の注記・チーム別内訳のいずれにも含めない。経理申請した時点で計上され、経理が「下書きに戻す」と外れる。判定は集計側と取得側で同じ定義を使う
- 月の判定は日付文字列の先頭 7 文字（YYYY-MM）の比較で行う（タイムゾーン変換による月ズレを避けるため Date は使わない）
- 案件開始日が NULL の案件（下書きを除く）の売上・費用と、entry_date が NULL の経理追加収支は「月未確定」として別枠表示する（支出エントリの経費は管理費）。teamleader は月次集計と同じく、全体共通（チーム未指定）の経理追加収支を月未確定にも数えない
- business.amount は NULL 許容のため NULL は 0 として扱う
- 定期費用: 適用期間内（`start_month <= 選択月の月初日 AND (end_month IS NULL OR 選択月の月初日 <= end_month)`。end_month の月を**含む**）かつ支払月に一致する月に計上する。支払月は適用開始月を起点にサイクル間隔（月払い=毎月、四半期払い=3ヶ月ごと、年払い=12ヶ月ごと）で決まる。月割り按分はしない
- 経理追加収支はマイナス金額を許容する。チーム別収支ではエントリのチームへ振り分ける。案件ではないため案件別収支・分類別の粗利には含めない
- 算入先ルールの変更は過去の月・確定済みの月にも遡って適用される。確定済みの月は確定明細（エントリの種別を保存済み）から毎回集計し直すため、明細は確定時点のまま、粗利・管理費の内訳だけが新ルールで表示される（経常利益は変わらない）
- 損益調整（実績額修正）がある明細行は、集計・表示のすべてで実績額（= 元データ + 調整）を用いる（[4.16.5](#4165-損益調整実績額修正)）

##### 案件別収支・分類別の粗利

- 案件別収支は 案件 → 案件内訳（売上明細 → 費用明細）の 2 階層。チームは案件行の列で表示する。並びは案件 ID 昇順、内訳は各 ID 昇順
- 案件の粗利 = 売上明細の実績額合計 − 費用明細の実績額合計（片方のみの案件は他方を 0 とする）
- 分類別の粗利は、売上・案件費用を案件の分類（matters.category。大分類まで。小分類集計はしない）別に「売上 − 案件費用」で集計し、損益計算書の「案件」行の内訳として表示する。粗利の降順。売上のない分類に費用のみがあれば粗利マイナスの行になる。案件費用の品目別集計は行わない
- 経理追加収支を分類別の粗利に含めないのは、支出分類（交通費など）と案件の売上分類が同じ列に混在しないようにするため
- チーム別収支は明細ごとのチームで集計する（確定済みの月で一部の明細だけ反映した場合など、同じ案件でも明細によってチームが異なることがあるため）
- 管理費は費目（recurring_costs.item）別に集計する
- 不変条件
  - 損益計算書の売上総利益の「案件」行 ＝ 案件別収支の「案件の合計」＝ 分類別の粗利の合計
  - 「案件」＋「経理追加収支（収入）」＝ 売上総利益
  - 定期費用 ＋ 経理追加収支（支出）＝ 管理費合計
  - 売上総利益 − 管理費合計 ＝ 経常利益
  - チーム別収支の合計 ＝ サマリーカード（売上 / 粗利 / 経常利益）

#### 4.16.3 表示内容

月次タブは次の順に表示する。

- 対象月ピッカー（確定済み・確定後に変更ありの月は目印付き）。左右の「前月」「翌月」ボタンでも月を切り替えられる
- サマリーカード（売上 / 粗利 / 経常利益）
- 損益計算書テーブル（売上総利益 → 管理費 → 経常利益。列は 元データ / 調整 / 実績）
  - 売上総利益は「案件」（展開で分類別の粗利）と「経理追加収支」（収入エントリがある月のみ。展開で明細）
  - 管理費合計は費目別内訳（展開で定期費用明細。実績額修正の対象単位）と「経理追加収支（支出）」（支出エントリがある月のみ。展開で明細）

  - 案件別: 案件別収支。案件行に「案件を表示」（閲覧専用の案件詳細モーダル。閲覧可否は RLS が担保）。案件の分類・チームは明細行の分類・チームの一覧で表示し、明細によって異なる案件には注意アイコンを付ける。「調整あり」バッジ・元データ変更の警告・実績額修正・タイトル編集は明細行単位
  - チーム別: 経理担当者・管理者・チームリーダー（閲覧のみ）。管理費は定期費用 ＋ 経理追加収支（支出）。チームに紐づかないものは「全体共通」
- 対象行が当月に存在しない損益調整の警告と削除操作（経理担当者・管理者のみ）
- 月未確定の注記（該当データがある場合のみ）
- **モバイル表示（md = 768px 未満。CSS のみで切り替え）**: 損益計算書テーブルは「元データ」「調整」列を隠して「実績」だけを表示し（調整ありは調整アイコンで分かる）、一括開閉ボタンはテーブルの上に出す。案件別収支は案件ごとのカード（展開トグル付きの案件 ID・案件名、確定後の変更アイコン、名称変更・タイトル編集、分類バッジ、チーム名、売上・案件費用・粗利、「案件を表示」）。展開した明細は「売上／費用バッジ・明細名（費用は品目）・実績額」と「調整内訳・確定後の変更・タイトル編集・実績額を修正」の 2 段の行。一覧の上に一括開閉、末尾に「案件の合計」カードと注記。チーム別収支はチームごとのカード（チーム名、売上・案件費用・粗利・管理費、区切り線の下に太字の経常利益）。md 以上は従来どおりの表
- 経理担当者・管理者向け: 「前月の経理追加収支をコピー」（[4.19.3](#4193-機能)）、経理追加収支・定期費用マスタへの管理リンク（表示中の対象月を `?month=` で引き継ぐ）

#### 4.16.5 損益調整（実績額修正）

- 案件の売上・案件費用・管理費が実際の入金・支払額と一致しない場合（請求額の変更、値引き、ある月だけ金額が異なる定期費用など）に、経理担当者・管理者が月次タブ上で対象月の実績額へ修正できる
- 元データ（business.amount / costs.price / recurring_costs.price）は書き換えず、対象行×対象月ごとの調整（差分）を別テーブル（profit_loss_adjustments）に持つ。表示・集計は「元データ + 調整 = 実績」
  - 案件の売上・費用は担当者の入力で、申請後の編集が差し戻し検知の対象になるため、経理が直接書き換えると担当者の案件が変わり差し戻し検知も誤発火する
  - 定期費用マスタは適用期間で全月に反映されるため、金額欄を直すと全月が変わる。恒久的な改定は「打ち切り＋新行」運用（[4.18.4](#4184-金額改定の運用)）とし、単月の差異のみ本機能で扱う
- 入力は実績額のみ。保存時に調整額（= 実績額 − 保存直前の元データ金額）を計算し、その時点の元データ金額（スナップショット）と調整理由（必須）とともに保存する。実績額を元データと同額に戻すと調整自体が削除される。明細行単位で即時保存する
- 元データ変更の検知: 調整の保存後に元データの金額が変わった行には「元データが変更されています」の警告を出す。調整額は自動では追従しない（経理が再確認して更新するか削除する）
- 対象行が別の月に移動した（案件開始日の変更等）・案件が下書きに戻された場合、調整は対象月に留まる。その月の集計対象に対象行が無ければ損益には反映せず、「対象行が当月に存在しません」として削除を促す。対象行そのものが削除された場合は調整も自動削除される
- 確定済みの月（[4.16.7](#4167-月次収支確定)）の調整は追加・更新・削除できない（「確定済み」をオフにしてから編集する。RLS と保存関数でも拒否）
- 役割の分担: 案件・定期費用マスタに紐づく差異は本機能、それらに紐づかない収入・支出は経理追加収支（[4.19.1](#4191-概要)）
- 権限: 編集は経理担当者・管理者のみ（RLS でも担保）。チームリーダーは全チームの実績額・調整ありの表示・調整理由を閲覧できる（編集はできない）

#### 4.16.6 表示タイトルの変更

- 経理担当者・管理者は、損益計算書上の案件・明細の名称を、損益計算書上だけで有効な表示タイトルに変更できる（案件名は担当者が案件管理用に付けた名前で、報告資料としては分かりにくい場合があるため）
- 対象: 案件別収支の案件行、案件内訳の売上明細・費用明細、管理費の明細。チーム・分類・品目・費目の見出しと経理追加収支（/extra-entries で内容を直接編集できる）は対象外
- 対象行単位で全月共通。元データ（matters.title / business.name / costs.name / recurring_costs.name）は変更せず、案件画面・経理用一覧にも影響しない（`has_updates` も立たない）。保存先は profit_loss_labels（[database.md 3.14](database.md#314-profit_loss_labels-テーブル)）
- 行単位で即時保存。空欄で保存すると上書きを削除して元の名称に戻る。前後の空白は除去し 200 文字以内。上書き中の行には「名称変更」バッジを付け、元の名称をツールチップで示す
- チームリーダーは上書き後のタイトルを表示する（編集不可。RLS でも拒否）
- タイトルは金額・集計に影響しないため、月次収支確定・変更検知・編集ロックの対象外。確定済みの月でも常に最新の上書きタイトルを表示する（確定明細に保存した名称は、元の行が削除された場合のフォールバックのみ）

#### 4.16.7 月次収支確定

損益計算書は表示のたびにライブ集計するため、締めた後の月でも案件の変更が過去の損益に反映され、確認・報告済みの数字が黙って変わる。これを防ぐため、月ごとに「確定」で収支をスナップショットとして固定して表示する。

##### 確定・確定解除

- 月次タブの「確定済み」スイッチ（経理担当者・管理者のみ。確認ダイアログあり）
  - **オン**: 当月をサーバ側でライブ集計し直してスナップショットを保存する（クライアントから送られた金額は使わない）。保存後（編集ロックが掛かった後）にもう一度集計し、確定処理中に他の経理担当者が保存した変更があれば取り直す
  - 画面を開いた後に他の経理担当者が同じ月を確定していた場合は、既存の確定を上書きせず「既に確定されています。再読み込みしてください」と表示する（他の担当者の確定値・見送りを黙って置き換えないため）
  - **オフ**: スナップショットと変更の見送り記録を削除し、ライブ集計に戻る。損益調整・経理追加収支の編集ロックも解ける。既に解除済みだった場合は成功扱いにせず再読み込みを促す
  - オフ → オンで、その時点のライブ集計から新しく取り直す（確定者・確定日時は新しいもの。最終反映・見送りの記録は残らない）
- 確定の対象は案件（売上・費用）・定期費用・経理追加収支・損益調整のすべて（月の損益を丸ごと固定）。下書きの案件は含まない。「月未確定」枠は対象外（常にライブ表示）
- 確定月の順序制約はない（前月未確定でも当月を確定できる）。確定操作の履歴は全件保持せず、最新の確定者・確定日時と最終反映者・反映日時のみ持つ

##### 確定後のデータ種別ごとの扱い

| 対象                   | 確定済みの月での編集                                                           | 確定済みの月への反映                                                                        |
| ---------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 案件（担当者の編集）   | できる（ロックしない）                                                         | すぐには反映しない。変更アラート → 経理が明細ごとに反映 / 見送り                            |
| 定期費用マスタ         | できる（1 行が複数の月に効くためロックしない）                                 | **反映しない・アラートも出さない**。反映したい場合は「確定済み」をオフ → 再度オンで取り直す |
| 損益調整（実績額修正） | **できない**（「確定済み」をオフにしてから編集する）                           | -                                                                                           |
| 経理追加収支           | **できない**（同上）                                                           | -                                                                                           |
| 表示タイトル           | できる（金額・集計に影響しないため対象外。[4.16.6](#4166-表示タイトルの変更)） | 常に最新のタイトルを表示する                                                                |

##### 編集ロック（損益調整・経理追加収支）

- ロックする操作: 確定済みの月の調整の追加・更新・削除、確定済みの月の日付のエントリの追加・更新・削除、確定済みの月へ / からの日付の変更、確定済みの月への「前月の経理追加収支をコピー」（日付未入力のエントリは対象外）
- UI は該当ボタンを無効化して「確定済みの月です。編集するには損益計算書で『確定済み』をオフにしてください」と示す。サーバ側でも判定し、該当があれば何も書き込まずエラーを返す。DB の RLS でも担保する（[database.md 5.7 / 5.12 / 5.14](database.md#514-profit_loss_closings--profit_loss_closing_lines-テーブル)）。案件の明細・定期費用の削除に伴う損益調整の CASCADE 削除は妨げない

##### 確定後の表示

- 確定済みの月は、損益計算書・案件別収支・サマリーカード・チーム別収支・全体共通（参考）・年間推移のすべてをスナップショットから表示する（未確定の月はライブ集計）。集計処理はライブと共通
- 名称（案件名・取引先名・コスト名・定期費用名）は確定の対象外で、元の行が存在する限り最新の名称（上書きタイトルがあればそれ）を表示する。元の行が削除された明細のみ確定時点の名称
- 月次タブに「確定済み（日時 確定者）」と、反映の記録があれば「最終反映」を表示する。年間推移では確定済みの月の列見出しに鍵アイコンと背景色を付ける。定期費用マスタ画面では、適用期間に確定済みの月が含まれる行に「確定済みの月（YYYY年M月〜）の損益計算書には反映されません」と注記する
- チームリーダーにも確定値を表示する（全チーム分。操作はできない）
- 「対象行が当月に存在しない損益調整」はライブの状態で判定する。確定済みの月では、対象行が確定明細に含まれていれば「確定値に算入済み」、含まれていなければ「確定値にも含まれていません」と表示し、削除は「確定済み」をオフにしてから行う

##### 変更検知・反映・見送り

確定後に案件側で起きた変更を検知して経理に知らせ、経理が明細ごとに「反映」または「見送り」を選ぶ。

- **検知の対象は案件（売上明細・案件費用明細）のみ**。定期費用マスタの変更は反映もアラートもしない。損益調整・経理追加収支は確定中はロックされる
- 当月のライブ集計の案件明細と確定明細を `(source_type, source_id)` で突き合わせて差分を算出する（純粋関数 `diffClosingLines`。DB トリガーや変更フラグは使わず、`has_updates` とは別物）
- 差分の種類: 追加（確定後に申請された / 明細追加 / 案件開始日の変更で他月から移ってきた）、削除（案件・明細の削除 / 下書きに戻された / 案件開始日の変更で他月へ移った・未入力になった）、金額変更、区分変更（分類・チームの変更。金額変更と同時もあり得る）。名称だけの変更は差分に含めない
- 案件開始日の変更で確定済みの月 A から確定済みの月 B に移った場合、A に「削除」、B に「追加」が出る。相手側の月を併記し、相手側も確定済みなら片方だけ反映すると両月の合計がずれる旨を注意する。相手側の月の情報を取得できなかった場合は反映を無効にして再読み込みを促す（見送りは確定値を変えないため可能）。削除の差分には理由（他月へ移動 / 開始日が未入力 / 下書きに戻された / 削除された）を併記する
- **通知（経理担当者・管理者のみ）**: 損益計算書画面の上部に「確定後に未反映の変更がある月」の警告バナー（月名で月次タブのその月へ）、月ピッカーの強調、年間推移の列見出しのアラートアイコン、月次タブの差分一覧と案件行・明細行の変更アイコンを出す。件数は未処理の差分（反映も見送りもしていないもの）だけを数える。Slack 等への通知はしない
- **バナー・月ピッカー・年間推移の対象は、当月（JST）を含む直近 24 ヶ月（当月の 23 ヶ月前以降。当月より後の確定済みの月も含む）の確定済みの月に限る**。件数の集計は対象月のライブ明細・確定明細・見送り記録をすべて読むため、全期間を対象にすると取得量が運用期間に比例して増えるため。24 ヶ月は前年度（7月〜翌6月）の全月を常に含む長さで、決算・申告期間中も前年度の変更を見落とさない
  - 対象外の確定済みの月は、月次タブで開いたときに差分を計算して警告・差分一覧を表示し、反映・見送りもできる（月ピッカーでは確定の下線のみ、年間推移ではアラートアイコンが出ない）
  - 目印が出ていなくても変更が無いとは限らないため、対象外の確定済みの月があるときは「確定後の変更の目印は YYYY年M月以降の確定済みの月が対象です（それより前の月は月次タブで開くと差分を確認できます）」と注記する（バナー内・対象外の月を表示中の月ピッカー下・対象外の月を含む年度の年間推移の表の上。経理担当者・管理者のみ）
  - 「元データの `updated_at` が確定日時より新しい月」に絞る方式は採らない。案件・明細の**削除**（CASCADE 含む）は `updated_at` を残さず検知できず、案件開始日の変更で他月へ移った場合も変更後の行から移動元の月が分からないため
- 差分一覧: 選択・種類・区分・チーム・案件名・明細名・変更前 → 変更後・差額・「案件を表示」。選択した差分を反映した場合の影響額（売上 / 案件費用 / 粗利 / 経常利益の「確定値 → 反映後」）を表示する。選択は月を切り替えると解除する（他月へ移動した明細は両月で同じ明細になるため、持ち越すと選んでいない月で反映してしまう）
- 「選択した変更を反映」「すべて反映」（確認ダイアログで影響額を再表示）: 選択した明細だけ、確定明細を最新の値に置き換える（確定者・確定日時は保持し、反映者・反映日時を記録）
- 反映・見送りの Server Action は、選択した `(source_type, source_id)` と画面で見ていた明細の状態（在否・実績額・チーム・分類）を受け取り、値はサーバ側でライブ集計し直したものを使う。画面で見ていた状態と現在が食い違う明細があれば「再読み込みしてから操作してください」として拒否する（利用者が見ていない変更を反映・見送りしない）
- **見送り**（確認ダイアログあり）: 確定明細を変えずにアラート・件数から外す。見送りはその時点の変更内容に対して行い、見送り後にさらに変更されれば再び未処理として出す。見送り済みは差分一覧の下の折りたたみに日時・見送った人とともに表示し、「見送りを取り消す」「選択した変更を反映」もできる。見送り記録は、反映したとき・「確定済み」をオフにしたとき（CASCADE）・確定直後の取り直しで削除する。差分が解消した明細の見送り記録は表示しない
- チームリーダーにはアラート・差分一覧・操作を表示しない（見送り記録は RLS でも読めず、反映・見送りも拒否される）
- **担当者への注意（案件詳細モーダル）**: 案件の作成・編集時、保存済みまたは入力中の開始日の月が確定済みの場合（確定済みの月へ / からの変更も含む）は、確定済みの月に計上される案件には「この案件は確定済みの月（YYYY年M月）の損益計算書に計上されています。変更は経理の確認後に損益計算書へ反映されます」、下書き（新規作成を含む）には「この案件の開始日は損益計算書で確定済みの月（YYYY年M月）です。経理申請すると、経理の確認後にその月の損益計算書へ反映されます」と表示する（保存は妨げない。経理用の詳細モーダルも同様）。確定済みの月の一覧は profit_loss_closings の SELECT（ログインユーザー全員に許可）から取得する

### 4.17 年間推移表示 (F018)

- 年度は **7月〜翌6月**（「2026年度」= 2026年7月〜2027年6月）。年度セレクトの左右の「前年度」「翌年度」ボタンでも切り替えられる（選択肢の端では無効）。列は 12 ヶ月＋年度合計、行は 売上 / 案件費用 / 粗利 / 管理費 / 経常利益
- 確定済みの月（[4.16.7](#4167-月次収支確定)）は確定明細から集計し、列見出しに鍵アイコン・列全体に薄い背景色を付ける（凡例を表の上に出す。チームリーダーにも表示）。確定後に未処理の変更がある月はアラートアイコン（経理担当者・管理者のみ。対象範囲は 4.16.7）。年間推移では差分そのものは計算しない
- 表の下に売上・利益の推移グラフを表示する: 折れ線（売上 / 案件費用 / 粗利 / 管理費）と棒（経常利益）を 1 枚に重ねる。横軸は 12 ヶ月（年度合計を含まない）、縦軸は全系列共通の金額軸（0 の基準線あり。経常利益がマイナスの月は棒が 0 より下に伸びる）。表と同じデータ・同じ表示範囲（チームリーダーは自チームの数字のみ）を使い、追加の取得はしない
- グラフは Recharts を含むため遅延読み込みし、年間推移タブの表示中だけ描画する（非表示パネルで幅 0 のまま再計測・再描画しないため）。スタイルシート（`@mantine/charts/styles.css`）もグラフ側で読み込み、全ページ共通の CSS に含めない
- 取得の注意は [8](#8-損益計算書のデータ取得)

### 4.18 定期費用マスタ管理 (F019)

#### 4.18.1 概要

- 定期的にかかる管理費（家賃・システム利用料など）を登録する。支払サイクル（月払い / 四半期払い / 年払い）に対応し、支払月の損益計算書に支払額が全額算入される
- 実レコードは生成せず、適用期間と支払サイクルから計算で算出する（登録・変更が即座に全期間へ反映される）
- 経理担当者・管理者のみ。一覧の追加・編集・削除を一括保存する（ステージング編集方式）

#### 4.18.2 登録項目

| 項目          | 説明                                               | 必須 |
| ------------- | -------------------------------------------------- | ---- |
| 名称          | 例: オフィス家賃                                   | ○    |
| 品目          | 品目マスタ（select_options の item）から選択       | ○    |
| 支払額（1回） | 円。支払サイクル1回あたりの金額（年払いなら年額）  | ○    |
| 支払サイクル  | 月払い / 四半期払い / 年払い（既定: 月払い）       | ○    |
| チーム        | チームマスタから選択。未選択 = 「全体共通」        | -    |
| 適用開始月    | 最初の支払月。以降はサイクル間隔ごとに支払月となる | ○    |
| 適用終了月    | この月まで損益に算入する（含む）。未設定 = 継続中  | -    |
| コメント      | 備考                                               | -    |

#### 4.18.3 保存時の注意

保存は通信失敗時にも自動で再実行しない（新規行の二重登録を防ぐため）。追加・更新・削除を並列に送るため、失敗時は一部だけ反映されている（または応答だけ失われて反映済みの）可能性がある。そのため失敗時・成功時とも、最新の一覧を取り直すまで編集・保存を止め、取り直した実際の状態に同期する（保存前の古い一覧で上書きしない）。取り直しに失敗した場合は「再読み込み」を案内する。

#### 4.18.4 金額改定の運用

金額が改定された場合は、既存行の適用終了月を改定前月にして打ち切り、新しい金額の行を改定月から新規登録する（過去の月の損益が遡って変わるのを防ぐ）。確定済みの月がある場合も編集はできるが、確定値には反映されず変更アラートも出ない（反映したい場合は [4.16.7](#4167-月次収支確定)）。

### 4.19 経理追加収支管理 (F020)

#### 4.19.1 概要

- 案件管理と定期費用マスタだけでは実際の収支と一致しないため、案件に紐づかない収入・支出を経理担当者・管理者が登録・編集できる
- 収入エントリは「請求額 → 売上」「経費 → 案件費用」の両方を計上できる（例: 受託収入とその外注費）。支出エントリは経費のみで、管理費に算入する
- 日付（entry_date）の属する月の損益計算書に算入される。日付未入力は「月未確定」として別枠表示する
- マイナス金額を許容する（互換性のため残す）。**案件・定期費用マスタに紐づく差異は損益調整（[4.16.5](#4165-損益調整実績額修正)）で扱い、それらに紐づかない収入・支出のみ本機能で扱う**。案件費用の減額調整を目的としたマイナスの支出エントリは管理費の減額になる

#### 4.19.2 登録項目

| 項目       | 説明                                                                               | 必須        |
| ---------- | ---------------------------------------------------------------------------------- | ----------- |
| 種別       | 収入 / 支出                                                                        | ○           |
| 分類       | 収入時は収入分類マスタ、支出時は支出分類マスタから選択（種別で選択肢が切り替わる） | ○           |
| 日付       | 損益計算書に算入する月の判定に使用。未入力 = 月未確定                              | -           |
| 請求書番号 | 自由入力。**収入時のみ**                                                           | -           |
| 内容       | 自由入力。過去の入力値をサジェスト                                                 | ○           |
| 請求先     | 自由入力。過去の入力値をサジェスト。**収入時のみ**                                 | -           |
| 責任者     | メンバー（profiles）から選択                                                       | ○           |
| チーム     | チームマスタから選択。未選択 = 「全体共通」                                        | -           |
| 請求額     | 円・税別。マイナス可・0 不可。**収入時のみ**                                       | ○（収入時） |
| 経費       | 円・税別。マイナス可・0 不可。収入時は任意（収入に紐づく経費）、支出時は必須       | ○（支出時） |
| 決済方法   | 決済方法マスタから選択。**支出時のみ**                                             | ○（支出時） |

#### 4.19.3 機能

- `/extra-entries` で一覧表示・追加・編集・削除（ステージング編集方式・一括保存）。分類・決済方法の選択肢は項目管理（F016）で編集する。内容・請求先のサジェスト候補は直近 12 ヶ月分と月未確定分（表示中の対象月に限らない）
- 編集は経理担当者・管理者のみ。チームリーダーは損益計算書上で明細を閲覧できる（自チーム＋全体共通）
- **対象月**: 月ピッカー（確定済みの月は目印付き。「前月」「翌月」ボタンでも切り替えられ、未保存時の破棄確認・切替中の編集ロックは同じ）。初期値は `?month=YYYY-MM` が有効ならその月、無効・未指定なら当月（JST）。表示するのは対象月のエントリと月未確定のエントリのみ（取得もサーバ側で絞る）。月未確定の行は常に先頭に「月未確定」バッジ付きで表示する（放置を防ぐ）。新規行の日付の初期値は対象月の 1 日。対象月が確定済みなら追加ボタンを無効化する
- 未保存の編集がある状態で対象月を変えるときは破棄確認する。切替中は前の月の行を編集・保存できない。日付を別の月に変えて保存した行はその月の一覧に移る
- **確定済みの月のロック**（[4.16.7](#4167-月次収支確定)）: 確定済みの月のエントリは追加・編集・削除できず、確定済みの月へ / からの日付変更もできない（入力欄・削除ボタンを無効化し、日付の選択肢から確定済みの月を除外。サーバ側・RLS でも拒否）
- **一括保存の仕様**
  - 画面に読み込んだ時点と比べて追加・削除・編集した行だけを送る。確定済みの月のエントリがあっても他の月のエントリは保存でき、読み込み後に他の利用者が保存した内容を古い値で上書きしない
  - 編集した行が読み込み後に他の利用者に削除されていた場合は、何も保存せず再読み込みを促す（削除した行が既に削除済みなら、その削除だけ省いて保存する）
  - 保存は 1 トランザクション。保存前の確認後に月が確定されるなどで 1 件でも保存できなければ何も保存せずエラー（一部だけ保存された状態は残らない）
  - 必須・金額のチェックは送る行だけに行う（編集していない行・ロックされた行の既存の値で保存が止まらない）
  - 通信失敗時にも自動で再実行しない（新規行の二重登録を防ぐため）。保存できたか分からない場合は、最新の一覧を取り直すまで編集・保存を止めて実際の結果に同期する（保存されていなかった編集内容は入力し直す）。取り直しに失敗した場合や、保存・確定などで古くなった一覧を取り直せないまま表示する場合は、その旨と「再読み込み」を表示して編集・保存を止める。staleTime 経過による再取得（月の切り替え時など）の失敗では、警告のうえ編集・保存できる。画面を離れている間に一覧が古くなった場合（前月コピー・確定の後など）は、開き直したときに取り直す
- **前月コピー**: 損益計算書の月次タブの「前月の経理追加収支をコピー」（経理担当者・管理者のみ。RLS でも書き込みは同ロール限定）
  - 表示中の月の前月に entry_date が属するエントリを、entry_date を当月の同日（当月にその日が無ければ末日）に置き換えて当月分として一括登録する。分類・内容・請求先・責任者・チーム・金額・決済方法を引き継ぎ、請求書番号は常に空にする。損益調整はコピー対象に含まない（単月の差異は繰り越す性質のものではないため）。entry_date が NULL の明細は対象外
  - 確認ダイアログでコピー件数・対象月を表示する（当月に既存分があれば追記になる旨も案内）。前月分が 0 件・表示中の月が確定済みのときはボタンを無効化する（確定済みの月へのコピーはサーバ側・RLS でも拒否）
  - 複製元は登録直前にサーバ側で id 指定により改めて取得する（確認から実行までの他利用者の編集・削除を反映するため）。当月に既に同一内容（種別・分類・内容・責任者・チーム・金額）の明細がある行は二重コピーとみなしてスキップする。既存行の確認と登録は DB 側で対象月ごとに直列化する（`copy_extra_entries`。[database.md 5.7](database.md#57-extra_entries-テーブル)）ため、複数の経理担当者が同時にコピーしても二重登録されない。全件スキップ・一部スキップはその旨を通知する

#### 4.19.4 損益計算書への反映

- 収入エントリ: 請求額を売上合計へ、経費（入力時のみ）を案件費用合計へ算入し、売上総利益の「経理追加収支」行（請求 − 経費）に合計する
- 支出エントリ: 経費を管理費合計へ算入し、管理費合計の「経理追加収支（支出）」行に合計する
- 分類別の粗利・案件別収支には含めない（[4.16.2](#4162-計上ルール)）。チーム別収支には算入する（チーム未指定は「全体共通」）
- 明細は損益計算書の展開行で確認できる（独立した表は持たない）

### 4.20 事前収支申告 (F021)

#### 4.20.1 概要

- 各チームのチームリーダーが、翌月のチーム収支（見込み収入・見込み支出）を明細付きで申告する
- 申告期限は毎月 20 日（当月 20 日までに翌月分を申告）。期限は未申告リマインドのトリガーであり、期限後の申告・修正も可能。ただし月単位で確定された月は編集できない（[4.20.8](#4208-月次確定)）
- 閲覧はチームリーダー・経理担当者・管理者のみ。チームリーダーは全チームの申告（ヘッダ・明細）を**閲覧のみ**でき、作成・編集・削除は自チーム分のみ（他チームとの比較・全体把握のため）。定期明細（[4.20.7](#4207-定期明細毎月固定の収入支出)）は従来どおり自チームのみ
- 1 チーム × 1 対象月につき申告は 1 件（`budget_declarations` の UNIQUE 制約）。合計金額はヘッダに持たず明細から集計する
- **申告の状態は 3 つ**。ヘッダ行があるだけでは「申告済み」にならず、申告フォームの「申告を完了する（申告済みにする）」チェックを入れて保存したときだけ申告済みになる（`completed_at` が設定される）
  - 未申告: ヘッダ行がない
  - 入力中: ヘッダ行はあるが未完了（明細を何回かに分けて入力する途中）
  - 申告済み: `completed_at` が設定されている。明細 0 件でもチェックを入れれば申告済み（申告する内容がない月を「申告内容なし」として完了できる。一覧では「明細なし」と表示する）

#### 4.20.2 申告項目

| 項目         | 説明                                                                                       | 必須 |
| ------------ | ------------------------------------------------------------------------------------------ | ---- |
| 対象月       | 申告対象の月（月初日で保持）。一覧の初期表示は JST 基準の翌月                              | ○    |
| チーム       | チームマスタの値。チームリーダーは自チームのみ                                             | ○    |
| 申告者       | 最終更新したメンバー（`declared_by`）                                                      | ○    |
| 申告完了     | 「申告を完了する」チェック。ON で申告済み、OFF で入力中（`completed_at` / `completed_by`） | -    |
| コメント     | 補足コメント（自由入力）                                                                   | -    |
| 明細：種別   | 収入 / 支出                                                                                | ○    |
| 明細：分類   | 収入は案件分類マスタ（category）、支出は品目マスタ（item）                                 | ○    |
| 明細：内容   | 自由入力（例: ○○受託案件、外注費）                                                         | ○    |
| 明細：金額   | 見込み金額（円・税別）。正の値のみ（符号は種別が決める）                                   | ○    |
| 明細：担当者 | 収入・支出ごとの担当者（メンバー。全メンバーから選択、チーム所属で絞らない）               | -    |

#### 4.20.3 一覧ビュー

- 対象月のチーム × 申告状況（申告済み / 入力中 / 未申告のバッジ）を全チーム分一覧する。入力中の申告の金額も全チーム合計に含める。チームリーダーは他チームの行を「明細を表示」で参照できるが、「申告する / 編集する」ボタンは自チームの行にだけ表示する
- 未申告のチームも行として並べる（未申告の可視化が目的のため）。チームマスタから外れた（無効化・改名された）チームの申告も末尾に表示し、取りこぼさない。チームマスタから外れたチームのチームリーダーには、未申告でも自チームの行を末尾に表示する（申告できなくなることを防ぐ）
- 収入合計・支出合計・差引（収入 − 支出）を行に表示する。選択月の全チーム合計（収入合計・支出合計・収支。収支がマイナスなら赤字）は画面上部のサマリーに表示し、テーブルのフッター合計は置かない。行を開くと明細とコメントを参照でき、複数チームを同時に開ける（対象月を切り替えると開閉状態はリセット）
- 明細（一覧の展開表示・入力フォームとも）は収入 = 淡い青 / 支出 = 淡い赤の行背景で見分け、支出の金額は赤字で表示する（ライト / ダークどちらでも判別できるよう Mantine の theme-aware な色を使う）
- **モバイル表示（md = 768px 未満。CSS のみで切り替え）**: 一覧はチームごとのカード（チーム名・申告状況バッジ、収入合計・支出合計・差引、申告者・最終更新、明細の開閉と申告する / 編集するボタン）、展開した明細は「内容・金額」と「種別・分類・担当者」の 2 段の行、入力フォーム（申告・定期明細）は 1 明細 1 ブロックの縦並び（フォームのモーダルは全画面）。md 以上は従来どおりの表
- 申告者名・担当者名は `profiles` の RLS で読めない場合に「-」表示となる（申告状況・集計は表示する）。ただしチームリーダーは自チームの `profiles` しか読めないため、他チームの申告者・担当者名は全メンバーの id / 名前のみを返す SECURITY DEFINER 関数 `get_member_options`（[database.md](database.md)）で補って表示する（取得に失敗したときは RLS で読めた名前のみ・読めなければ「-」）

#### 4.20.4 作成・編集・削除フォームの機能

- 対象月は一覧で選択中の月に固定。チームは、チームリーダーは自チーム固定、経理担当者・管理者は選択可（ただし編集時は対象月・チームの組み合わせを変えないためロールに関わらず固定）。選択可能な場合にチームを変えると、入力済みの明細行は「変更するとクリアされる」旨を確認のうえクリアする（別チームの明細一式を誤って別チームとして保存することを防ぐ）
- 明細の分類の選択肢は種別に連動する。種別を変更すると分類は未選択に戻る
- **定期明細の自動展開**: 新規作成フォームを開くと、対象月が適用期間内の定期明細（[4.20.7](#4207-定期明細毎月固定の収入支出)）が「定期」バッジ付きの明細行として展開される（チームを変えると切り替わる。確認ダイアログは出さない）。編集時（既存の申告を開いた場合）は展開しない（二重計上防止）。展開された行も編集・削除してから保存できる
- **前月の明細をコピー**（新規作成時のみ）: 前月・同チームの申告明細（種別・分類・内容・金額・担当者。コメントは前月固有の可能性が高いため対象外）を明細行の末尾に取り込む。定期明細の自動展開との重複を避けるため、初期投入は定期明細を優先し、前月コピーは利用者の明示操作とする。前月の申告が無い・明細が 0 件のときは無効化。既に明細行があるときは追記の確認を経る。コピー元は書き込み可能な自チームの前月申告のみ
- **マスタ未登録の分類**: 前月コピー・定期明細の自動展開・無効化後の状態で分類がマスタから消えている（無効化・改名された）場合、値は保持して空欄に見せないが、そのままでは保存できない。「（マスタ未登録）」付きの選択不可の選択肢で表示し、行とフォーム上部に警告を出す。保存には有効なマスタ値への選び直しが必須
- **申告済みチェック**: フォーム内の「申告を完了する（申告済みにする）」チェックボックスで完了 / 取消を行い、明細と同じ保存操作でまとめて保存する（一覧の行ボタンから直接完了 / 取消する操作は無い）。既存の申告を開くとフォームは現在の状態を初期値とし、チェックを外さずに保存すれば申告済みのまま、外して保存すると入力中に戻る。権限は申告の書き込み権限と同じ（自チームのチームリーダー・経理担当者・管理者）で、確定中の月は変更できない。`completed_by` は `auth.uid()` から DB 関数内で解決し、クライアントからは受け取らない。**完了済みの申告を（チェックを外さずに）再保存しても `completed_at` / `completed_by` は更新せず、最初に完了した日時と完了者を保持する**（チェックを外して入れ直すと更新される）
- 保存前のバリデーション: 種別・分類・内容が未入力 / 金額が 0 以下 / 分類がマスタ（収入 = category、支出 = item）に無い場合は保存を中止する。明細 0 件（コメントのみ）は許容する
- 保存は確認ダイアログを経る。DB 関数 `save_budget_declaration`（[database.md 5.9](database.md)）を 1 回呼ぶだけで、ヘッダの作成 / 更新と明細の差し替え（既存明細を全削除して登録し直す）を単一トランザクションで行う（失敗時は保存前に完全にロールバック）。保存直前にサーバ側で最新の分類マスタと照合し、クライアントの表示に依存せず直接の Server Action 呼び出しでの回避も防ぐ。新規作成が `(target_month, team)` の一意制約に違反した場合（他の担当者が作成済み）は案内して中止する（一覧から編集するよう促す）
- 削除は編集フォームからのみ。確認のうえヘッダを削除し、明細は `ON DELETE CASCADE` で同時に削除される
- 書き込み権限（チームの判定）は RLS が最終防御。フォーム表示・Server Action の双方で事前チェックし、権限不足を案内する
- 確定済みの月は全ロールで作成・編集・削除できない（[4.20.8](#4208-月次確定)）

#### 4.20.6 未申告 Slack リマインド

- Vercel Cron が毎日 09:00 JST（`0 0 * * *` UTC。`vercel.json`）に `app/api/cron/budget-declaration-reminder/route.ts` を実行する。`Authorization: Bearer ${CRON_SECRET}` が一致しなければ 401
- リマインド対象日と日ごとの文面は `budget_declaration_reminder_days`（1 日 1 行。[database.md 3.11](database.md#311-budget_declaration_reminder_days-テーブル)）で管理し、デプロイなしで編集できる（DB 取得に失敗したら既定 15 / 18 / 20 日・既定文面にフォールバック）。JST の今日の行が無ければ何もしない（200 でスキップ）。**行を 0 件にするとリマインド自体が停止する**（cron は動作するが常にスキップ）
- 文面はメッセージ 1 行目のテンプレートで、プレースホルダは `{month}`（対象月。例: 2026年10月）と `{deadline}`（期限日）。既定文面は `【事前収支申告リマインド】{month}分の事前収支申告が未申告・未完了のチームがあります。`。未知のプレースホルダ・空・1000 文字超は保存できない。例: 15 日は予告、20 日は「本日期限」のように日ごとに変えられる
- 編集は `/budget-declarations` の「リマインド設定」（admin / accounting のみ。[5.3.14](#5314-事前収支申告画面)）。保存は全置換 RPC（`replace_budget_declaration_reminder_days`）で 1 トランザクションに行う
- 対象日に、翌月（JST）分の申告が無い、または未完了（入力中）のチームを抽出する（全チームが申告済み（完了）なら通知しない。翌月が確定済み（[4.20.8](#4208-月次確定)）なら通知せずスキップする）。未申告チームのチームリーダー（`profiles.is_teamleader = true` かつ team が一致）の `slack_id` でメンションし、当日の文面の後ろにチーム名・期限（毎月 20 日）・申告ページ URL を付けて 1 通にまとめて `SLACK_WEBHOOK_URL` へ送る。`slack_id` 未設定のリーダーやリーダー不在のチームはメンションなしでチーム名のみ通知する
- cron ハンドラは認証セッションを持たないため、`app/utils/supabase/budgetDeclarationReminderData.ts` に限り `SUPABASE_SERVICE_ROLE_KEY`（RLS を完全にバイパスできる強力なキー）の server-only クライアントで読み取る。キー自体の権限はこの用途に限定されないため、クライアントへ露出させない
- 申告ページ URL は Vercel が自動設定する `VERCEL_PROJECT_PRODUCTION_URL` / `VERCEL_URL` から組み立てる（追加の環境変数は不要）

#### 4.20.7 定期明細（毎月固定の収入・支出）

- 毎月同額で発生する収入・支出（保守契約の月額収入、固定の外注費など）を一度登録すれば、以降の月の新規申告作成時に明細として自動で載る。定期費用マスタ（[4.18](#418-定期費用マスタ管理-f019)）と同様の考え方だが、対象は事前収支申告の明細で、テーブルも別（`budget_recurring_items`。[database.md 3.12](database.md#312-budget_recurring_items-テーブル)）
- 登録項目: チーム（チームリーダーは自チーム固定）/ 種別 / 分類（種別連動）/ 内容 / 金額 / 担当者（任意）/ 適用開始月 / 適用終了月（NULL = 継続中）
- **反映方式は「申告作成時に明細として展開する」**。新規申告フォームを開いたとき、対象月が適用期間内（`start_month <= 対象月 <= end_month` または `end_month` が NULL）の定期明細が初期明細として投入される。保存すると通常の申告明細になり、以降は申告ごとに個別に編集・削除できる（定期明細マスタは変わらない）。既存の一覧・集計・リマインドのロジックは変更不要で、「未申告」「入力中」の判定も定期明細の有無に影響されない（集計時に合算する方式は、未申告チームでも定期分が金額に載って「未申告」の意味が変わるため採らなかった）
- 既存申告の編集時は展開しない（二重計上防止）。適用終了月を過ぎた定期明細は以降の月に展開しない。金額改定は定期費用マスタと同じ運用（既存行を打ち切り、新しい行を追加）
- 分類がマスタから消えた既存行は「（マスタ未登録）」付き・選択不可で表示して警告し、保存時に選び直しを必須とする（サーバ側 `bulkSaveBudgetRecurringItems` でも最新の分類マスタと照合）。無効値のまま残すと以降の新規申告へ自動展開され続けるため、無効化後は速やかに選び直す
- 管理画面 `/budget-declarations/recurring` はチームリーダー（自チームのみ）・経理担当者・管理者（全チーム）が登録・編集・削除できる（UI と RLS の両方で担保。[database.md 5.11](database.md#511-budget_recurring_items-テーブル)）。定期費用マスタ画面と同じステージング編集（一括保存）。適用終了月が適用開始月より前の入力は保存できない

#### 4.20.8 月次確定

- 対象月ごとに「確定」でき、確定は**その月の全チームの申告を一括**で対象にする。確定中の月は**全ロール**で申告の作成・編集・削除ができない（UI はボタン無効化とメッセージ表示、DB は RLS・トリガー・`save_budget_declaration` で拒否するため API / RPC の直接呼び出しでも拒否される）
- 確定 / 確定解除できるのは経理担当者・管理者のみ（損益計算書の月次収支確定と同じ権限。`BUDGET_CLOSING_WRITE_CLASSES`）。チームリーダーは確定状態（確定済みバッジ・確定日時・確定者）の閲覧のみ
- 確定解除で再び編集できる。確定の実行時に未申告・入力中のチームがあっても確定できる（未完了のまま締める運用を許容する。未完了チームがあるときの警告は設けていない）
- 対象月ピッカーでは確定済みの月に下線を付ける（`CustomMonthPicker` の `getMonthIndicator`）。「前月」「翌月」ボタンでも月を切り替えられ、開閉状態のリセットは同じ
- 確定月には未申告 Slack リマインドを送らない（[4.20.6](#4206-未申告-slack-リマインド)）。確定状態の取得に失敗した場合は fail-open（未確定として通常どおり送る）
- 損益計算書の月次収支確定（[4.16.7](#4167-月次収支確定)）とは独立した機能で、相互に連動しない

#### 5.3.9 管理画面

- `/dashboard` は `/dashboard/users` へリダイレクトする（ヘッダー・トップページの入口は `/dashboard` のまま）。各画面は URL で直接開ける
- PC（768px 以上）は左サイドメニュー、モバイルは上部の横並びタブで「ユーザー管理」「項目管理」を切り替える。未保存の変更があれば切り替え前に「未保存の変更があります。破棄して移動しますか？」と確認する（[4.14](#414-ユーザー管理-f015) / [4.15](#415-マスタデータ管理-f016)）
- ユーザー管理: 名前・メール・権限・チームリーダー・チーム・Slack ID を表示する（ID は表示しない）。画面見出しは「ユーザー管理」。権限の表示名はメンバー / 経理 / 管理者（保存する値は public / accounting / admin）。チームリーダーは別列のチェックボックス。変更した行は左端のオレンジの線と「変更あり」バッジで示して「N 件変更あり」を表示し、変更が無い間は「一括保存」「変更を破棄」を押せない。チームはチームリーダーにチェックを入れた場合必須
  - 並び順（PC・モバイル共通）: 権限（管理者 → 経理 → メンバー。それ以外・未設定は末尾）→ チームリーダー（チェック済みを先頭）→ チーム（項目管理の表示順。選択肢に無いチームは選択肢のチームの後ろ、チーム未設定は末尾）→ 名前（日本語の照合順）。並べ替えるのは読み込み時と一括保存の成功後だけで、編集中は動かさない（権限やチームを変えた行が動くと見失うため）
  - 権限ごとのセクション: 権限ごとに「管理者（1 名）」のように人数付きの見出しで分け、管理者 → 経理 → メンバー の順（`CLASS_DISPLAY_RANK`。チームリーダーのフラグでセクションは分けない）、権限が未設定・不正な値のユーザーは末尾の「未設定」セクションに置く。該当者がいないセクションは表示しない。PC は各セクションに同じ列の表、モバイルは各見出しの下にカードを並べる。セクション内の並び順は上記のとおり（チームリーダー → チーム → 名前）。「一括保存」「変更を破棄」・入力チェック・未保存の変更の警告は画面全体で 1 つ。**編集中に権限を変えた行は、一括保存に成功するまで元のセクションに残し**、成功した時点で新しいセクションへ移す（並べ替えのタイミングと同じ。編集中の行が消えて見失うのを防ぐ）
  - チームの背景色: コード内の固定パレット（文字が読みやすい淡い色。`app/utils/userListGroup.ts`）を、チームの表示順（項目管理の並び順）に割り当てる。DB は変更しない。項目管理でチームの並び順を変えると割り当ても変わる。チーム数がパレットの色数を超えたら先頭から使い回す。無効化・改名されて選択肢に無いチームとチーム未設定の行には色を付けない（チームリーダーのチェックを外すとチームが空になるため、色が付くのは主にチームリーダーのユーザー）
  - 一覧の取得失敗は画面全体のエラー（再試行ボタン）。チーム選択肢の取得失敗は、その旨を表示してチーム欄は現在の値のみ表示する
- 項目管理: PC は左にカテゴリ一覧（案件・費用で使う項目: チーム / 分類 / 品目、追加収支で使う項目: 収入分類 / 支出分類 / 決済方法。件数と未保存のドットを表示）、右に選択中のカテゴリの編集パネルを表示する。モバイルは一覧の代わりに Select で切り替え、変更があるときだけ画面下の固定バーから保存・破棄する。カテゴリを切り替えても編集中の内容は残り、選択中のカテゴリは URL の `?type=` に反映する。未入力・重複は入力欄と Alert の両方で示す。取得失敗は該当カテゴリのパネル内にエラーを表示する（画面全体はエラーにしない）

#### 5.3.14 事前収支申告画面

- 対象月ピッカー（初期値は翌月。確定済みの月は下線付き）と、その直下のサマリー（選択月の全チーム合計 = 収入合計・支出合計・収支。収支がマイナスなら赤字）。サマリー内に確定状態（確定済みバッジ・確定日時・確定者）を表示し、admin / accounting にのみ「確定済み」スイッチを表示する（確認ダイアログを経て確定 / 解除。[4.20.8](#4208-月次確定)）。確定済みの月は全ロールで「申告する / 編集する」を無効化し、作成・編集・削除できない旨のメッセージを表示する
- チーム別申告状況テーブル（全ロールで全チームを表示。フッター合計は置かない）。未申告チームは金額欄を「-」とし明細表示を無効化、差引がマイナスの行は赤字。状態はバッジ（未申告 / 入力中 / 申告済み）で示し、明細 0 件の申告済みは「明細なし」を併記する。「申告する」（未申告）/「編集する」（入力中・申告済み）でフォームモーダルを開く。チームリーダーの他チーム行は操作欄が「閲覧のみ」（明細の展開は可）。「定期明細を管理」で定期明細画面へ遷移する
- 「リマインド設定」ボタン（admin / accounting のみ描画。teamleader / public には描画しない）でモーダルを開き、未申告 Slack リマインドの対象日（JST。1〜31 を複数選択）と、選択した日ごとの文面を編集する。選択した日ごとに文面の Textarea（新規に選んだ日は既定文面）・プレースホルダの説明・サンプル値のプレビューを表示し、未知のプレースホルダや空の文面はエラー表示で保存できない。日のチップを外しても編集中の文面は保持し、再選択で復元する（保存されるのは選択中の日のみ）。29〜31 日は月によって存在せず、その月はスキップされる
  - 保存済みの対象日が 0 件のときはボタンの横に「リマインド無効」バッジを表示する（設定の取得に失敗した場合は状態が不明なため表示しない）。モーダルでも、保存済みが 0 件なら「現在リマインドは無効です」、選択をすべて解除したなら「保存するとリマインドが無効になります」と警告する
  - 開くたびに最後に保存された対象日で初期化し、閉じると未保存の選択は破棄する。保存は確認ダイアログを経て（対象日を空にする場合は停止になる旨を案内）実行し、成功したら閉じる（失敗・確認キャンセル時は開いたまま）
  - 保存中と確認ダイアログの表示中はモーダルを閉じられない（キャンセル・保存を無効化し、× を非表示にし、Esc・オーバーレイのクリックも受け付けない）
  - 設定の取得に失敗した場合は、モーダル内に「リマインド設定の取得に失敗しました」のエラーのみを表示する

## 8. 損益計算書のデータ取得

損益計算書は行数が運用期間に比例して増えるため、取得は次の前提で作る。

- PostgREST は 1 リクエストの行数を max_rows（既定 1000。埋め込みリソースの配列にも掛かる）で打ち切る。集計元は id のキーセット方式（id > 直前の最大 id）でページングして全件集める（offset 方式と違い、取得中に前の行が削除されても読み飛ばさない）。確定明細・見送り記録は埋め込まずに別クエリでページングする
- 取得範囲は絞る: 月次は対象月＋月未確定（NULL）行、年間推移は年度 12 ヶ月＋NULL 行のみ。案件の売上・費用は `matters!inner` 側で「下書きでない AND（`start_date` が期間内 OR NULL）」、`extra_entries.entry_date` は「期間内 OR NULL」、定期費用は適用期間の重なり、損益調整は `target_month` の範囲で絞る。支払サイクルの計上判定は集計側で行う。年間推移が月単位の 12 回クエリにならないよう、まとめて並列に取得する（範囲境界の定義は `reportRangeBounds`）
- 表示タイトルは、取得した行の ID を種別ごとに集め、`in()` で 200 件ずつ分けて取得する（URL の長さと max_rows に掛からないため）。年間推移はタイトルを表示しないため取得しない
- 対象行が取得期間外へ移動した調整（`orphanedAdjustments`）のラベル解決用に、欠けている対象行だけを ID 指定で補完取得する（通常は 0 件。集計値は不変）
- 確定後の変更のバナー用の集計は、直近 24 ヶ月の確定済みの月に限り（[4.16.7](#4167-月次収支確定)）、連続する確定済みの月ごとにライブ明細・確定明細・見送り記録を並列に取得して月別に差分を数える（離れた確定済みの月の間にある未確定の月は取得しない）

## 9. エラーハンドリング

### 9.1 API エラー

- 書き込み（TanStack Query の mutation）は失敗しても自動で再試行しない（`QueryProvider` の既定 `retry: 0`）。コミット後に応答だけ失われた場合に再実行すると、INSERT を含む保存で行が二重に登録されるため。案件の更新・確認完了など冪等な書き込みも含めて一律とし、失敗時はエラーを通知して利用者に再操作を促す。読み取り（query）の再試行は従来どおり（`retry: 2`）

### 9.2 バリデーション

必須項目の確認と、請求日 ≤ 振込期限の確認（4.4 参照）をフォームで行う。フォーム固有のチェックは各機能の節を参照。
