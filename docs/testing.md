# テスト設計書

## 1. 概要

経理システムのテスト方針・対象・規約を定める。ユニット／コンポーネントテストは Vitest（`tests/`、`vitest.config.ts`）、CI は GitHub Actions（`.github/workflows/`）。E2E は未実装（3.6）。

- **前提環境**: Next.js 14（App Router）/ TypeScript（strict）/ Supabase / yarn
- **関連ドキュメント**: [setup.md](./setup.md) / [specification.md](./specification.md) / [database.md](./database.md)

## 2. テスト方針

### 2.1 テストピラミッドと優先度

```text
    E2E Tests (少数・当面は手動)
  Integration Tests (中程度・当面は対象外)
Unit Tests (多数・最優先)
```

- **優先度**: 変更頻度・影響範囲・障害時コストで決める。認可・ドメイン制限、案件ステータス遷移、金額集計（損益計算書を含む）、ビルド成立性を優先する。
- **対象範囲**: services 層は無く、ビジネスロジックは `app/utils/`（特に `app/utils/supabase/`）に集約されている。ユニットテストの対象はその**純粋ロジック**に絞り、Supabase クエリの薄いラッパーは対象外とする。UI は原則対象外だが、**権限別統合コンポーネント**（variant ごとの主要素の出る / 出ない）は Testing Library で固定する。

### 2.2 実行タイミング（PR / リリース前）

- **PR**: CI が自動実行する（型チェック、Lint（デバッグ出力検知を含む）、ビルド、ユニットテスト、フォーマットチェック。DB 関数は pgTAP）。ワークフローは 4 章。
- **リリース前（`main` → `release`）**: 影響範囲が広い変更（認可・middleware、案件ステータス遷移、損益計算書、主要画面の動線）は主要フローを手動確認する（3.6）。手順は `docs/release.md`。

### 2.3 テストデータ方針

- Unit テストは固定のインメモリ・フィクスチャ（型は `app/lib/database.types.ts` 由来）で独立させ、Supabase・Slack 等の外部依存は直接叩かない。
- 統合確認が必要な場合はローカル Supabase（`supabase start` / `supabase db reset` で `supabase/migrations/` を適用）を使い、当面は自動テストに含めない。
- RLS はユニットテストで検証できないため、`supabase/migrations/` のレビューと 3.7 の手動確認でカバーする。失敗モードはエラーではなく**サイレント 0 行**（画面は空のまま描画される）。

### 2.4 可観測性

- 確認観点ごとにチェック（ジョブ）を分離し、テスト名・ジョブ名から目的が読み取れる命名にする。
- 開発時のデバッグ出力（`console.log` / `console.info` / `debugger`）は ESLint（`no-console`（`error` / `warn` は許可）・`no-debugger`）で検知する。障害調査用の `console.error` 等は意図的に残す。

### 2.5 ユニットテストの要否判断

機能の追加・修正時は以下で判断する。新規・既存を問わず適用し、テスト済みコードを修正したら対応するテストも更新する。

#### テストを書くべきもの

| 対象                                                | 理由                                                                                                      | 例                                                                                                                                                   |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 認可・ドメイン制限ロジック                          | 壊れるとセキュリティ事故につながる。手動確認では全パターンの網羅が困難                                    | `hasClassAccess` / `visibleNavItems`（`app/utils/permissions.ts`）、`isAllowedEmailDomain`（`app/utils/constants.ts`）、`middleware.ts` のルート判定 |
| 状態遷移・分岐・計算を含むビジネスロジック          | 案件ライフサイクル（下書き→経理申請中→経理確認完了→完了）と金額集計はシステムの中核。回帰時の影響が大きい | `matterValidation.ts` / `useUpdateMatter` のバリデーション、`matterCalc.ts` の金額集計、`profitLossLogic.ts` の支払サイクル判定・月次集計            |
| 日付・タイムゾーン変換                              | JST/UTC の月ズレは静かに壊れ、発見が遅れる                                                                | `toMonthString`（`app/utils/formatter.ts`）、`bulkUpsertCostInfo` 等の日付フォーマット処理                                                           |
| 外部API連携のメッセージ組み立て・エラーハンドリング | 障害時の挙動はテストなしでは確認できない                                                                  | Slack 通知（`app/utils/slack/sendMessageToSlack.ts`、`app/actions/slack/`）                                                                          |

上記以外（Supabase クエリの薄い CRUD ラッパー、UI の見た目、`page.tsx` のデータ受け渡し、定数・型定義など）は、RLS・型チェック・Lint・ビルド・レビューでカバーするためユニットテストは原則不要。迷う場合はロジックの複雑さと障害時の影響度で判断する。

ただし **DB アクセスまわりでもサイレント障害につながるエラーハンドリングはテスト対象**とする。(1) 取得失敗を「0 件」として描画しない、(2) 削除・更新の件数を検証して 0 件を成功にしない、(3) 明細削除を CASCADE に委譲して原子性を保つ（カタログ #16 / #17）。

### 2.6 テスト容易化リファクタリング方針

判定・計算・整形ロジックが副作用（DB 呼び出し・ダイアログ・通知）や module-private な関数と密結合でテストできない場合は、次の方針で扱う。

- **第一推奨: 純粋関数の分離**。`"use server"` の付かないファイル（`app/utils/` 直下など）へ切り出して export する。確認ダイアログ（`confirmAction()`、`@mantine/modals`）は呼び出し側（コンポーネント / フック）の責務とする。
- **暫定手段: グローバルモック**。テストを先行させたい場合に限り jsdom + `vi.stubGlobal` 等で代替する。恒久策にしない。
- リファクタリングは**テスト追加とは別 PR** とし、挙動変更がないことをレビューで担保する。
- 案件の必須・日付バリデーションは作成（`addMatterInfo`）と更新（`useUpdateMatter`）の両方で実行する。下書きの更新時は `start_date` を必須にしない（DB 上 nullable な既存データを他項目だけ編集して保存できるようにするため）。経理申請時（`is_fixed === true`）は必須。
- 未対応: `bulkUpsertCostInfo` / `bulkUpsertBusinessInfo` の `isNew` / `isRemoved` 振り分けと日付整形が DB 呼び出しと同一関数内にある（カタログ #9）。純粋関数として切り出し、JST 月ズレの有無を確認して必要なら `toMonthString` と同様のローカル時刻基準へ直す。

## 3. テスト対象と観点

### 3.1 ビジネスロジックユニットテスト

外部 I/O（Supabase / Slack / ブラウザ API）から切り離して確認する。対象の詳細はテスト対象カタログ（5 章）。

- 案件ステータス遷移の判定（新規申請 / 申請後更新（差し戻し検知 `has_updates`）/ 完了 / 差し戻し）
- 入力バリデーション（必須項目、請求日と振込期限の日付順序）
- 金額集計（`total_amount` / `total_cost` / `unchecked_cost_count`。`isRemoved` 行の除外、`isNew` の扱い）
- 損益計算書の集計: 支払サイクル（月払い / 四半期 / 年払い）の計上月判定、案件開始日基準の計上月と下書き除外、案件別収支（案件 → 案件内訳）・分類別粗利（案件のみ）・経理追加収支の算入先（収入は売上総利益、支出は管理費）・チーム別収支・費目別管理費・経常利益の算出と合計の一致、ロール別の集計範囲、チーム未指定（全体共通）費用の扱い、表示タイトルの解決
- 月次収支確定（確定明細 ⇔ 明細行の往復、確定済みの月のスナップショット表示、編集ロックの判定）と確定後の変更検知（追加・削除・金額変更・区分変更、見送りの状態判定、反映の内容と影響額）
- `isNew` / `isRemoved` による INSERT / UPDATE / DELETE の振り分け
- 日付フォーマット（JST での月ズレが起きないこと）

### 3.2 セキュリティテスト

単体で確認できる部分はユニット、実際の認証フロー・RLS に関わる部分は手動とする。

| 観点           | CI（自動）                                                                                                                               | 手動                                                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 認証制御       | ―                                                                                                                                        | 未ログインユーザーの `/login` リダイレクト（3.7）            |
| 認可制御       | `hasClassAccess` / `visibleNavItems` / ルートマッチングの判定ロジック（`ROUTE_PERMISSIONS` のロール別許可/拒否）                         | middleware 経由の実アクセス制御（権限クラス×ページ表は 3.7） |
| ドメイン制限   | `isAllowedEmailDomain`（完全一致のみ許可、`evil-future-tech-association.org` のような部分一致の拒否、null/空文字/大文字小文字/前後空白） | Google OAuth コールバックでの実挙動                          |
| データアクセス | ―（ユニットでは検証困難）                                                                                                                | RLS によるデータ分離。サイレント 0 行の切り分けは 3.7        |

### 3.3 型安全性テスト

- `tsc --noEmit`（`yarn typecheck`）と ESLint で型不整合を検知する。
- スキーマ変更時は `yarn db:types-local` で `app/lib/database.types.ts` を更新する（CLAUDE.md / setup.md）。CI での型再生成・差分チェックは未導入。

### 3.4 ビルドテスト

`yarn install --frozen-lockfile`（lockfile どおりに成功）と `next build` の完走を確認する。

### 3.5 コード品質テスト

- ESLint（`yarn lint`）: デバッグ出力の混入（`no-console` / `no-debugger`）と `@supabase/auth-helpers-nextjs` の import を検知する。
- Prettier（`yarn format:check`）: 未整形を検知する。

### 3.6 E2Eテスト（未実装・リリース前のみ）

リリース前（`main` → `release`）または影響範囲が大きい変更（認可、案件ステータス遷移、損益計算書、主要画面の動線）で、単一ブラウザで主要フローを 1〜2 本、手動で確認する（全網羅はしない）。

- ログイン → 案件作成（下書き）→ 経理申請 → 経理確認完了 → 完了
- 経理申請後の編集 → 経理画面での差し戻しハイライト → Slack 通知 → 差し戻し
- teamleader / accounting / admin / public 各ロールでの保護ページアクセス → 適切なリダイレクト
- 損益計算書の月次・年間表示（ロールによる表示範囲の違い）
- エラー境界（一時的な throw。確認後は戻す）→ 通知と再試行。存在しない URL → not-found

### 3.7 手動確認（RLS・権限クラス別）

認証フローと RLS はユニットテストでは検証できない。許可ロールの**実体**は `app/utils/permissions.ts` の `ROUTE_PERMISSIONS`（変更時はそこだけ直す）。本節は確認手順であり、ロール表のコピーではない。

認証スタックの入れ替え（Cookie 形式の変更）や権限別 UI の統合では、エラーなしで一覧が空になる事故を権限クラスごとに確認する。実施記録（実施日・実施者・環境・結果）と追加確認点は、その変更を含む PR 説明に残す。

#### 前提（データ準備）

- 確認用に、各ロールの Google アカウント（`@future-tech-association.org`）でログインできること
- データが空だと「RLS で見えない」と「本当に 0 件」を区別できない。**確認前に次が揃っていること**
  - `/matters` を確認する **public / teamleader / accounting / admin の各アカウント自身**が、1 件以上の案件を持っていること（このタブは自分の案件だけを取る。他人の案件では埋まらない）
  - `public` の案件に下書きと経理申請中が 1 件ずつあると、ライフサイクル確認に便利
  - 同じチームの別ユーザーの案件（teamleader の `/matters/team` タブ用）
  - 別チームの案件（teamleader の `/matters/team` タブには見えてはいけない）
  - `/matters/team` を確認する teamleader / admin は `profiles.team` が設定済みであること。未設定だとアプリがチーム案件を取らず空一覧を返す（RLS とは別原因）
  - 経理追加収支・定期費用マスタの行（accounting / admin 用）
  - `/profit-loss` の損益調整（実績額修正）確認用に、対象月の案件の売上・案件費用行と定期費用マスタの行がそれぞれ 1 件以上あること（実績額修正の対象がない月では操作を確認できない）。案件は**経理申請済み**（下書きは損益計算書に計上されない）で、案件開始日が対象月にあること
  - `/profit-loss` の月次収支確定・変更の反映 / 見送り確認用に、確定してよい検証用の月（案件・経理追加収支・定期費用がそれぞれ 1 件以上ある月）があること
  - `/budget-declarations` 用に、翌月分の事前収支申告が「申告済みのチーム」と「未申告のチーム」の両方があること（未申告行が出ることも確認対象のため、全チーム申告済みだと判定できない）
  - `/budget-declarations/recurring` 用に、適用期間が翌月を含む定期明細が 1 件以上あること（新規申告フォームを開いたときの自動展開を確認するため）
- ブラウザの開発者ツール Network で、対象 API が 200 かつ配列が空、になっていないかを補助的に見る。画面上は「スピナー後に空」でもエラーは出ない

#### 記号

- **表示**: ページが開き、想定どおりデータ行が見える
- **空でない**: 前提データを置いたうえで、一覧・表が 0 件のままにならない
- **拒否**: `/` へリダイレクト、または未ログインなら `/login`
- **対象外**: ナビに出ない / ロール的に開けない

#### 一覧のページネーション

件数が 1 ページ分（既定 24 件）以下ならページネーション UI は出ず全件表示になる。

- `/matters`・`/matters/team`・`/matters/accounting` で 25 件以上あるとき、2 ページ目に残りが表示され「N件中 X〜Y件を表示」が合っていること
- 表示件数（12/24/48/96）を切り替えると 1 ページ目に戻ること
- 経理用一覧で絞り込み（`ActiveMatterFilterBar`）を変えると 1 ページ目に戻り、フィルタ結果だけがページ分けされること（選択肢は全件から作られ、ページをめくっても変わらない）

#### 損益計算書

**計上基準・表示・構成**

- 請求日・支払期限が案件開始日と別の月でも、売上・費用は案件開始日の月に計上されること。下書きはどの月にも月未確定にも出ず、経理申請で計上され、「下書きに戻す」と外れること
- 月次タブの順序: サマリーカード（売上 / 粗利 / 経常利益の 3 枚。スマホ幅では縦並び）→ 損益計算書 → 収支の内訳タブ［案件別 / チーム別］→ 対象行なしの調整・全体共通（参考）・月未確定の注意
- 内訳タブの初期表示は「案件別」で、月を変えても選んだタブのままであること。teamleader には内訳タブが出ず案件別のみ。teamleader は自チームの案件のみで、全体共通（参考）は参考表示のみ
- 案件別収支は案件（ID 昇順。チームは列）→ 案件内訳（売上 → 費用）で展開でき、チームの見出し行・品目別の集計行・経理追加収支（案件外）の行が無いこと。案件の合計が損益計算書の「案件」行、チーム別収支の合計、サマリーカードと一致し、その旨の注記が出ること
- 売上総利益の下に「案件」（初期表示で分類別粗利を展開。支出分類は混ざらない）と「経理追加収支」（請求 − 経費。収入エントリがある月のみ）が並び、合計が売上総利益と一致すること
- 管理費合計の下に費目（定期費用）と「経理追加収支（支出）」（支出エントリがある月のみ）が並び、合計が管理費合計と一致すること。年間推移・チーム別収支の管理費に支出エントリの経費が含まれ、経常利益は内訳の変更前後で変わらないこと。日付未入力の支出エントリは月未確定の注記に「管理費」として出ること
- 「すべて開く」「すべて閉じる」がその表の行だけを開閉すること
- 年間推移で確定済みの月の列全体の背景色が変わり凡例が出ること（teamleader も同じ）。年度合計列の色と見分けられること

**RLS・同時実行・その他**

- API 直接呼び出しの拒否（RLS）: teamleader による確定・反映・見送り・タイトル保存、accounting による確定済みの月の損益調整・経理追加収支の変更がいずれも拒否されること（ローカルで各ロールの JWT により PostgREST へ直接リクエストして確認できる）
- 確定済みの月に計上される案件の明細を削除すると、その損益調整が CASCADE で削除されること（編集ロックに妨げられない）。確定値は変わらず、削除の差分として検知されること
- accounting 2 人（またはブラウザ 2 つ）で、A が未確定の月を開いたまま B がその月を確定して差分を見送る。A が「確定済み」をオンにすると「この月は既に確定されています…再読み込み…」と表示されて最新状態に切り替わり、B の確定者・見送りが残ること。「確定済み」を 2 つのブラウザでオフにした場合も、後からオフにした側は成功扱いにならず再読み込みを促されること
- `/extra-entries` を 2 つのブラウザで開き、A が行を削除して保存した後に B がその行を編集して保存すると「他の利用者に削除された行があります…」と表示され、B の他の追加・編集も保存されないこと。B が編集していない行は A の保存内容のまま上書きされないこと
- `/extra-entries` で A が 9 月の行の追加と 7 月の行の編集を入力したまま、B（損益計算書）が 7 月を確定してから A が保存すると「何も保存しませんでした」と表示され、9 月の追加も保存されないこと
- 確定と同じ月への損益調整・経理追加収支の保存の同時実行は、画面では再現できないため psql 2 セッションで確認する（後述「確定と書き込みの同時実行の再現手順」）。どちらの順でも「確定値 = ライブ集計」になること
- teamleader が作成した他チームの案件に accounting が損益調整を付けると、その月が未確定でも確定済みでも teamleader の画面で同じ実績額・調整額・調整理由が表示されること
- 確定後の変更の目印の対象範囲の注記: 件数集計の開始月（当月の 23 ヶ月前）より前の確定済みの月を用意する（ローカルでは `profit_loss_closings` に古い月の確定を作る）。accounting / admin では、未処理の差分がある月があるとき警告バナーの中、その古い月を月次タブで表示したとき月ピッカーの下、その月を含む年度の年間推移で表の上に「確定後の変更の目印は YYYY年M月以降の確定済みの月が対象です（…）」が出ること（開始月以降だけの月・年度では出ない）。teamleader ではどこにも出ないこと

**年間推移グラフ**

- 年間推移タブの表の下にグラフ「売上・利益の推移（YYYY年度）」が出る。売上・案件費用・粗利・管理費が折れ線、経常利益が棒で、凡例は表の行と同じ順。凡例にカーソルを合わせるとその系列が強調される
- 横軸は 7月〜6月の 12 か月分（年度合計なし）、縦軸は「100万」のような短い表記で 0 に基準線がある。経常利益がマイナスの月は棒が基準線より下に伸びる（色はプラスと同じ）
- タブを初めて開いたとき、読み込み中の表示から実グラフに切り替わっても枠の高さが変わらず下の要素がずれない
- スタイル（凡例が左寄せ横並び、ツールチップが枠付き）が効いていること。スタイルシートは遅延読み込みなので、別ページから遷移して初めて開いた場合と `/profit-loss` を直接再読み込みした場合の両方で確認する
- ツールチップの値が表の同じ月の値と円表記で一致すること（5 系列とも。確定済みの月・支出エントリがある月を含む）
- 年度切り替えで表と一緒にグラフも切り替わり、読み込み中・取得エラー・データなしではグラフが出ない。teamleader は自チームの数字だけ、accounting / admin は全体
- スマホ幅（375px 程度）で崩れず、グラフの枠内を横スクロールして 12 か月分を確認できる（ページ全体は横に広がらない）

#### 管理画面のユーザーリスト一括保存・並び順

admin で `/dashboard/users` を開き、確認用ユーザー（本番の運用アカウント以外）で確認する。

- **一括保存**: 2 人以上の権限・チーム・Slack ID を編集すると変更行がハイライトされ「N 件変更あり」と出る。「一括保存」→ 確認ダイアログで OK すると 1 回ですべて保存され、ハイライトと件数が消え、再読み込みしても保存後の値が出ること（PC 幅・モバイル幅とも）
- **変更を破棄**: 読み込み時点の値に戻り、ボタンが押せなくなること
- **入力チェック**: 権限を teamleader にしてチームが空のまま保存するとエラーがまとめて出て保存されないこと。teamleader 以外に変えるとチームが空になること
- **失敗時のロールバック**: ブラウザ A・B の両方で admin として開く。A で 2 人以上を編集したまま、B で A 自身の権限を admin 以外に変えて保存し、A で「一括保存」を押す。「何も保存しませんでした」と出て、A で編集したどの行も保存されず（B で再読み込みして確認）、A の編集内容が画面に残ること。確認後は SQL Editor 等で A の権限を admin に戻す
- **未保存の警告**: 編集したままリロード・タブを閉じようとするとブラウザの確認が出ること
- **画面切り替え時の確認**: 編集したままサイドメニュー（モバイルは上部のタブ）の「項目管理」を押すと確認が出て、キャンセルなら切り替わらず編集内容が残り、OK なら切り替わること。変更が無ければ確認なし。逆に `/dashboard/options` で項目名を編集したまま「ユーザー管理」を押しても同じ確認が出て、そのカードを「更新」して保存した後は確認なし。ヘッダーのリンク等からの遷移は確認しない（既知の制約）
- **項目管理の同じ名前の扱い**（`/dashboard/options` のチーム）: (1) 既存項目を削除して保存した後、同じ名前を追加して保存するとエラーにならず元の項目が再表示される（再読み込みしても 1 行）。(2)「X」を「X2」に変え同じ保存で「X」を追加すると両方保存される。(3) 有効な項目と同名を追加すると「「X」が複数あります…」と出て確認ダイアログなしで保存されない。(4) 削除済みの項目と同名に既存項目を改名すると「「X」と同じ名前の項目が既にあります（削除済みの項目を含む）。…」と出る。(5)「P」「Q」を「Q」「R」に同じ保存で変えると両方保存される。確認後は元に戻して保存する
- **不正な入力の拒否**: admin として `update_profiles` に必須キーの欠けた要素・同じ id の重複・許可値以外の class を渡すと `INVALID_INPUT` で何も更新されないこと（`docs/database.md`）
- **表示項目と並び順**: ID が表示されないこと。PC・モバイルとも権限（admin → accounting → teamleader → public）→ チーム（項目管理の表示順。選択肢に無いチームはその後ろ、未設定は末尾）→ 名前の順。編集しても保存するまで行の位置は変わらず、保存後（または再読み込み後）に並び直ること
- 権限の変更は対象ユーザーのトークン更新（最大約 1 時間）または再ログインまで middleware のロール判定に反映されない（既知の制約）。直後にメニューが変わらないのは不具合ではない

#### 確定と書き込みの同時実行の再現手順

月次収支の確定と、同じ月への経理追加収支・損益調整の保存が同時に走ったときに、書き込みが「確定値に含まれる」か「確定済みとして拒否される」のどちらかになる（確定値から漏れない）ことを、ローカル DB（`supabase db reset` 直後）に psql を 2 本つないで確認する。画面では時間幅が狭く再現できないため、`pg_sleep` でコミットを遅らせる。確定側（セッション B）は `closeProfitLossMonth` の「集計 → `save_profit_loss_closing` → コミット後に再集計 → 違えば取り直し」を SQL で模す（集計はアプリの `buildLiveMonthLines` の代わりに、経理追加収支と管理費（定期費用・損益調整）だけを補助関数で組み立てる）。

**本番・共有 DB では実行しない（ローカル DB 専用）**。検証用のユーザー・プロフィール・定期費用・補助関数を作り、確定・解除を行うため、終わったら `supabase db reset` で元に戻す。

以下の 4 つの SQL ブロックをそれぞれ `setup.sql`（準備）・`a.sql`（セッション A）・`b.sql`（セッション B）・`check.sql`（確認）に保存し、`psql -f` で流す。`a.sql` / `b.sql` はコミットまでの待ち時間を `-v hold=N`（秒）で渡す（`\gset` / `\if` を使うため psql で実行する）。シナリオごとの時間差はシェルで付ける:

```sh
PSQL="psql postgresql://postgres:postgres@127.0.0.1:54322/postgres"
$PSQL -f setup.sql
# シナリオ 1（書き込みが先）: A を開始し、1 秒後に B
$PSQL -v hold=3 -f a.sql & sleep 1; $PSQL -v hold=0 -f b.sql; wait
$PSQL -f check.sql
# （次のシナリオの前に、下の「シナリオ間のリセット」を実行する）
# シナリオ 2（確定が先）: B を開始し、0.5 秒後に A
$PSQL -v hold=2 -f b.sql & sleep 0.5; $PSQL -v hold=4 -f a.sql; wait
$PSQL -f check.sql
```

準備（`setup.sql`。postgres で 1 回。経理担当者 A / B と定期費用 1 件、補助関数 2 つ）:

```sql
INSERT INTO auth.users (id, email) VALUES
  ('11111111-1111-1111-1111-111111111111', 'a@example.com'),
  ('22222222-2222-2222-2222-222222222222', 'b@example.com');
INSERT INTO profiles (user_id, email, name, class) VALUES   -- profiles.id は 1（A）・2（B）
  ('11111111-1111-1111-1111-111111111111', 'a@example.com', '経理A', 'accounting'),
  ('22222222-2222-2222-2222-222222222222', 'b@example.com', '経理B', 'accounting');
INSERT INTO recurring_costs (name, item, price, start_month)       -- id は 1
  VALUES ('サーバ代', '通信費', 10000, '2026-01-01');

-- 当月のライブ集計（経理追加収支 + 管理費と損益調整）を save_profit_loss_closing の p_lines の形で返す
CREATE FUNCTION public.pl171_live_lines(p_month date) RETURNS jsonb LANGUAGE sql AS $$
  SELECT coalesce(jsonb_agg(l ORDER BY l->>'source_type', (l->>'source_id')::bigint), '[]'::jsonb) FROM (
    SELECT jsonb_build_object('source_type', 'extra_entry', 'source_id', e.id, 'name', e.description,
      'category', e.category, 'team', e.team, 'entry_type', e.entry_type, 'entry_date', e.entry_date,
      'billing_amount', e.billing_amount, 'expense_amount', e.expense_amount)
    FROM public.extra_entries e WHERE date_trunc('month', e.entry_date)::date = p_month
    UNION ALL
    SELECT jsonb_build_object('source_type', 'recurring_cost', 'source_id', rc.id, 'name', rc.name,
      'item', rc.item, 'team', rc.team, 'payment_cycle', rc.payment_cycle, 'source_amount', rc.price,
      'adjustment_amount', coalesce(a.adjustment_amount, 0),
      'actual_amount', rc.price + coalesce(a.adjustment_amount, 0), 'adjustment_reason', a.reason)
    FROM public.recurring_costs rc
    LEFT JOIN public.profit_loss_adjustments a ON a.recurring_cost_id = rc.id AND a.target_month = p_month
  ) s(l)
$$;
-- 確定明細を同じ形で返す
CREATE FUNCTION public.pl171_closed_lines(p_month date) RETURNS jsonb LANGUAGE sql AS $$
  SELECT coalesce(jsonb_agg(l ORDER BY l->>'source_type', (l->>'source_id')::bigint), '[]'::jsonb) FROM (
    SELECT CASE WHEN cl.source_type = 'extra_entry' THEN
      jsonb_build_object('source_type', cl.source_type, 'source_id', cl.source_id, 'name', cl.name,
        'category', cl.category, 'team', cl.team, 'entry_type', cl.entry_type, 'entry_date', cl.entry_date,
        'billing_amount', cl.billing_amount, 'expense_amount', cl.expense_amount)
    ELSE
      jsonb_build_object('source_type', cl.source_type, 'source_id', cl.source_id, 'name', cl.name,
        'item', cl.item, 'team', cl.team, 'payment_cycle', cl.payment_cycle, 'source_amount', cl.source_amount,
        'adjustment_amount', cl.adjustment_amount, 'actual_amount', cl.actual_amount,
        'adjustment_reason', cl.adjustment_reason)
    END
    FROM public.profit_loss_closing_lines cl
    JOIN public.profit_loss_closings c ON c.id = cl.closing_id
    WHERE c.target_month = p_month
  ) s(l)
$$;
```

#### 前月コピーの同時実行の再現手順

2 人の経理担当が同じ月へ「前月の経理追加収支をコピー」を同時に実行しても、同じ行が二重に登録されない（後のコピーは先のコピーのコミットを待ち、先に登録された行を同一内容としてスキップする）ことを、ローカル DB（`supabase db reset` 直後）に psql を 2 本つないで確認する。画面では時間幅が狭く再現できないため、`pg_sleep` でコミットを遅らせる。

**本番・共有 DB では実行しない（ローカル DB 専用）**。検証用のユーザー・プロフィール・経理追加収支を作るため、終わったら `supabase db reset` で元に戻す。

以下の SQL ブロックをそれぞれ `setup.sql`（準備）・`copy.sql`（コピー 1 回分）・`check.sql`（確認）に保存し、`psql -f` で流す。`copy.sql` は実行者（`-v sub=...`）とコミットまでの待ち時間（`-v hold=N` 秒）を変数で渡す:

```sh
PSQL="psql postgresql://postgres:postgres@127.0.0.1:54322/postgres"
$PSQL -f setup.sql
# A のコピー（コミットを 3 秒遅らせる）を開始し、その 1 秒後に B のコピー
$PSQL -v sub=11111111-1111-1111-1111-111111111111 -v hold=3 -f copy.sql & sleep 1
$PSQL -v sub=22222222-2222-2222-2222-222222222222 -v hold=0 -f copy.sql; wait
$PSQL -f check.sql
```

### 3.8 DB 関数のテスト（pgTAP）

SQL 関数（RPC）に移した業務ロジックは、Vitest では RPC をモックするだけになり判定そのものを検証できない。判定ロジックを持つ関数は pgTAP（`supabase test db`）で検証する。

- 配置: `supabase/tests/database/<対象>.test.sql`。1 ファイル = 1 トランザクション（`BEGIN; SELECT plan(N); ... SELECT * FROM finish(); ROLLBACK;`）で、テストデータは ROLLBACK で残らない
- 実行: ローカル Supabase を起動した状態で `supabase test db`。CI は `.github/workflows/db-test.yml`（`supabase/**` の変更時に `supabase start` → `supabase test db`）
- 権限つきの関数は `SET LOCAL ROLE authenticated` と `set_config('request.jwt.claims', ...)` で呼び出しユーザーを切り替えて検証する（RLS・FORBIDDEN の確認を含む）
- 対象: `budget_declaration_closings`（事前収支申告の全チーム閲覧と月次確定。`budget_declaration_closings.test.sql`）。teamleader の他チーム SELECT 可 / 他チームへの INSERT・UPDATE・DELETE 不可、public は閲覧不可、確定の権限（accounting / admin のみ。teamleader・他人名義・月初日以外は拒否）、確定月の全ロールでの書き込み拒否（ヘッダ・明細・`save_budget_declaration` / `delete_budget_declaration` の `MONTH_CLOSED`）、書き込みトリガー単体の拒否、確定者名の偽装防止、確定解除後の再編集。同時実行（排他ロック）は対象外
- 対象: `budget_declaration_completion`（事前収支申告の完了チェック。`budget_declaration_completion.test.sql`）。`save_budget_declaration` の `p_completed`（false で入力中、true で申告済み、明細 0 件でも完了可、NULL は変更なし、完了済みの再保存で `completed_at` を保持、チェックを外すと NULL に戻る）、`completed_by` が `auth.uid()` から解決されクライアントから指定できないこと、他チームのリーダーは変更不可、`completed_at` / `completed_by` の CHECK 制約、確定月での変更拒否（`MONTH_CLOSED`）。既存行の移行（全行を申告済みにする UPDATE）はマイグレーション適用時の一度きりの処理のため pgTAP の対象外で、適用時に手動確認した
- 対象: `budget_declaration_closing_trigger`（確定月の書き込みトリガー単体。`budget_declaration_closing_trigger.test.sql`）。RLS の確定月条件と同じ 42501 で区別できないため、別ファイル（別トランザクション）で書き込みポリシーを確定月条件なしに差し替え、ヘッダの INSERT / UPDATE / DELETE、未確定月から確定月への付け替え、明細の INSERT / DELETE がトリガー（`MONTH_CLOSED`）だけで拒否されることを確認する
- 対象: `copy_extra_entries`（前月コピーの重複判定。`copy_extra_entries.test.sql`）。全列一致のスキップ、1 列ずつ異なる行の登録、NULL 同士の一致、対象月の範囲外の行を重複とみなさないこと、戻り値の件数、空配列（0 / 0）、不正な入力（配列でない・要素がオブジェクトでない・`entry_date` が対象月外 / NULL → `INVALID_INPUT`）、FORBIDDEN。NOT NULL 列の NULL 同士の一致（`= ` への退行）は、テストのトランザクション内だけ `ALTER TABLE ... DROP NOT NULL` して確認する
- `db-test.yml` は `supabase/**` を変更する PR / `main` への push で実行する。リリース PR の品質ゲート（`release-pr.yml`）には含めない（DB の変更は `main` に入る PR の時点で検証済みで、`release` は `main` のある時点と一致するため）
- 関数の判定条件を変えたら、対応するテストも更新する。同時実行（排他ロック）は pgTAP では扱えないため、引き続き 3.7「前月コピーの同時実行の再現手順」で確認する

| `format-check.yml`       | `yarn format:check`（Prettier）                                            |
| `db-test.yml`            | `supabase start` + `supabase test db`（3.8。`supabase/**` の変更時）       |
| `release-pr.yml` ほか    | リリース用（`docs/release.md`）                                            |
| `supabase-keepalive.yml` | Supabase 無料プランの自動 Pause 防止（テストではない。`docs/setup.md`）    |

- トリガーは `pull_request` / `main` への `push` / `workflow_dispatch`（paths で絞るものあり。正は各 yml）。
- ジョブは観点ごとに分離し、失敗時にどの観点が壊れたか分かるようにする（2.4）。
- Vitest は TS / ESM / パスエイリアス（`@/*`）を軽量な設定で扱え、ファイル単位で node / jsdom を切り替えられる。関連プロジェクト（singularity-lab-portal）は Jest のため、規約（5 章）を揃えてノウハウを共有する。

## 5. テスト規約

### テストファイルの配置

- テストは `tests/` 配下に置き、対象コード（`app/`）の構造に寄せる。
  - 例: `app/utils/permissions.ts` → `tests/utils/permissions.test.ts`
  - 例: `app/components/CostBlock.tsx` → `tests/components/CostBlock.test.tsx`
- DB 関数の pgTAP テストは `supabase/tests/database/`（3.8）。

### ファイル名の命名

- 純粋関数は `*.test.ts`、JSX を含むコンポーネントテストは `*.test.tsx`（`*.spec.ts` は使わない）。「対象 + 期待する振る舞い」が想像できる名前にする。
- コンポーネントテストは先頭に `// @vitest-environment jsdom` を付ける（デフォルト環境は `node`）。TZ は `Asia/Tokyo` 固定。
- 描画は `tests/testUtils/renderWithMantine.tsx`（`MantineProvider` + `DatesLocaleProvider`）経由で行う。
  - このラッパーは Mantine の `Transition`（Menu / Popover / Modal など）の長さを 0 にしている（テーマの `respectReducedMotion` + `tests/setup.ts` の `matchMedia` スタブで `(prefers-reduced-motion: reduce)` だけを一致させる）。開閉は同期で反映され、rAF・タイマーは作られない。閉じたことは待たずに同期で `expect(...).not.toBeInTheDocument()` と書く（`waitForElementToBeRemoved` は待ち始めに要素が無いと失敗し、`waitFor` は無効化が外れても通ってしまい回帰に気付けない）。
  - 理由: Mantine 7.13 の `useTransition` は、開いている途中に閉じると予約済みの rAF を取り消さず、アンマウントしても消えない 150ms のタイマーが残る。jsdom の破棄後に発火すると `window is not defined` の未処理エラーになり、全テスト成功でも `yarn test` が断続的に失敗扱いになる。
  - 対象外: `Collapse` は開閉直後にアンマウントすると内部の rAF が残る。`@mantine/notifications` は reduced-motion でも 1ms のタイマーを使う（現状は `mockNotify` で描画しない）。これらを描画するテストは、開閉後に待ってから終える等を別途検討する。
  - `matchMedia` スタブは jsdom の全テストに効く（`ModalBase` のスクロールロック等、`useReducedMotion` を直接読む箇所は独自の `MantineProvider` を使うテストでも挙動が変わる）。ラッパーを使わず独自に `MantineProvider` を描画して開閉を伴う場合は、同様にトランジションを無効にする（例: `tests/utils/confirmAction.test.tsx` の `transitionProps: { duration: 0 }`）。
- `@/app/utils/notify` のモックは `tests/testUtils/mockNotify.ts` の `mockNotify()` を共有する。`toErrorMessage` は実装をそのまま使い、通知関数だけ `vi.fn` にする。ファクトリは `import("@/tests/testUtils/mockNotify")` で読み（相対パスにしない）、手書きの `vi.mock("@/app/utils/notify", …)` を増やさない。

### テストの検証対象

- **検証する**: 入力に対する出力（返り値）、副作用の結果（状態変化）、エラー時の振る舞い。返り値を持たない関数は副作用の結果（更新値・更新対象）を検証する。
- **検証しない**: 内部実装の呼び出し手順（クエリメソッドをどの引数で呼んだか等）。モックは外部依存の切り離しに使い、呼び出し引数の逐次検証は原則行わない。
